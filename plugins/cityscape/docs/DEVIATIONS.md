# Deviations from Monaco

Cityscape behaves like Monaco (vscode `src/vs/editor` at the commit of monaco-editor 0.52.2): expected values come from vscode's own tests, ported, or from recordings of the real Monaco, never from Cityscape. This file lists the intended differences, and only those. Each entry says what differs, why, and how it is tested.

Differences that only follow from Haxe (overloads merged into one method, static methods renamed with a `Static` suffix, `Event<void>` as `VoidEvent`...) are API conventions, described in [PORTING.md](PORTING.md); they change no behaviour and are not listed here.

## Decided in the plan, to be detailed as they are implemented

- **Rendering by Glaze instead of the DOM.** The view (`cityscape/view`) draws with Glaze; Monaco's DOM view parts are not ported.
- **Chrome from the Glaze kit.** Scrolling and scrollbars, popovers (hover, diagnostics), the suggest list, menus, the find widget and the color picker are the kit's, not Monaco's DOM widgets. Scroll positions are therefore not compared with recordings.
- **No minimap.** The `minimap` option and the minimap decorations are accepted and ignored.
- **Typed decoration style.** Decorations take a typed style (colors, font style, background, borders, joined ranges, hidden ranges) in addition to Monaco's CSS class names, which remain accepted as keys of registered styles.
- **Hidden text inside a line.** Monaco only hides whole lines; Cityscape can hide a range inside a line (through the line projections of the view model).
- **Per editor theme override.** The theme is global to a `Cityscape` context like Monaco's; an editor can override it.

## Option values

- **Options set to null.** Haxe has a single `null` where JavaScript has `undefined` and `null`: an option set to null is read as unset, so it takes its default. In Monaco a `null` reaches the validator (`readOnly: null` gives `false` there, the default `false` here too; `lineNumbers: null` gives `'off'` in Monaco and the default `'on'` here). Tests: `EditorOptionsTruthTest` (the Monaco truths do not include null inputs), `EditorConfigurationTest` (issues 94931 and 102920, where both agree).
- **Values of the wrong type copied as they are.** A few Monaco validators copy a value without checking its type (`gotoLocation.multipleDefinitions` and the other `multiple*` fields, `rulers[].color`). Cityscape keeps such a value only when it has the declared type (a string), and otherwise uses what Monaco uses for a missing value (`'peek'`, `null`). Values of the right type behave the same. Tests: `EditorOptionsTruthTest` (`gotoLocation`, `rulers` cases).

## Model

- **Regular expressions on the native targets.** Find (`TextModel.findMatches`, `TextModelSearch`) and word definitions use JavaScript regular expressions. On JavaScript they are the native `RegExp`. On hxcpp they run on PCRE2 10.42 (Haxe's `EReg`), with the source translated so that the JavaScript meaning is kept: `\w`, `\d`, `\b` are ASCII only, `\s` is JavaScript's set, `.` stops at `\n`, `\r`, U+2028 and U+2029, `^` and `$` follow JavaScript (also around `\r` with `m`), `\uXXXX`, `\u{...}`, `\v`, `\0`, `[]`, `[^]` and `\p{Script=...}` are supported. Differences left: a lookbehind of variable length is rejected by PCRE2 (the search then finds nothing, like an invalid pattern), a backreference to a group that did not take part fails instead of matching the empty string, lone surrogates in a pattern are rejected (in the searched text the result is undefined), case insensitive matching uses PCRE2's Unicode case folding. Tests: `RegExpTest` (JavaScript results, checked against the native `RegExp` by the Node run), `TextModelSearchTest` (all of vscode's cases pass on both targets).
- **Integer positions.** Line numbers, columns and offsets are `Int`: the NaN, float and `undefined` coordinates that Monaco's validation accepts (and floors) cannot be represented. vscode's tests for them are not ported (`EditorModelTextModelTest`, `TextModelCreateSnapshotTest`). On hxcpp, decoration offsets are 32 bit (Monaco's are 53 bit numbers): vscode's 'force delta overflow' interval tree test is not ported.
- **Undo without confirmation.** Monaco asks for a confirmation before undoing an element of another undo source or flagged `confirmBeforeUndo`; there is no dialog service here, the undo proceeds. Errors while undoing or redoing drop the stacks of the resource like Monaco's and go to `Errors.onUnexpectedError` (Monaco also shows a notification). Elements spanning several models (`MultiModelEditStackElement`, workspace elements) are not supported yet.

## Tokenization and themes

- **Background tokenization with a frame budget.** Monaco tokenizes the lines of a model attached to an editor in idle callbacks (`runWhenGlobalIdle`, until the idle deadline, yielding every 1 to 2 ms). Ceramic has no idle callback: the `BackgroundScheduler` of the `Cityscape` context runs the background tokenizers of all its models on the app's update event, with one time budget per frame shared by all of them (`budgetMs`, 4 ms by default), in turn. Which lines are tokenized, in which order, and the resulting tokens are Monaco's; only the timing differs. The visible lines are tokenized synchronously when an editor's visible range changes, like Monaco. Tests: `TextMateTruthTest.testBackgroundSchedulerTokenizesAttachedModels`, `asyncTestBackgroundTokenizationRunsInFrames`.
- **Registries per context.** Monaco's global `TokenizationRegistry`, `ModesRegistry` and language associations are fields of a `Cityscape` context (`tokenizationRegistry`, `modesRegistry`, `languageService`). Tokenizer factories resolve synchronously (`getOrCreate` returns the support instead of a promise). File name patterns (globs) of language associations are not supported yet.
- **Built-in theme rules are not changed by inheriting themes.** In Monaco, `StandaloneTheme.tokenTheme` appends the `editor.foreground`/`editor.background` rule of an inheriting theme to the rules array of the built-in base theme itself (`rules = baseData.rules; rules.push(rule)`), so the rule leaks into the next theme computed from the same base (a theme without `editor.foreground` then gets the foreground of another theme). Cityscape copies the array. Test: `StandaloneThemeServiceTest.testInheritedThemesDoNotChangeBuiltinData`.
- **TextMate token colors change live.** A theme with TextMate rules (`tokenColors` or tmTheme `settings`) sets the token color map of the context and retokenizes the models (visible lines at once, the rest in the background), like VS Code. loreline-monaco gives its theme to vscode-textmate once, so a theme change there only reaches the editor chrome; the tokens and colors for a given theme are the same. Test: `TextMateTruthTest.testLiveThemeChange`.
- **Language configuration from user settings.** Monaco's language configuration service also reads the settings `editor.language.brackets` and `editor.language.colorizedBracketPairs`; Cityscape has no configuration service: only the configurations registered with `languageConfigurationService.register` apply.

## View and rendering

- **Typed decoration style.** Next to Monaco's class names, `IModelDecorationOptions` takes typed styles: `inlineStyle` (like `inlineClassName`), `style` (like `className`), `lineStyle` (a whole line, like `className` with `isWholeLine`), `glyphMarginStyle`, `linesDecorationsStyle`, `lineNumberStyle`, `marginStyle`, and injected text takes `inlineStyle`. A style (`IDecorationStyle`) has a color, font style and weight, opacity, underline, strikethrough, font features, a background with a corner radius and vertical padding, a border, and `join` (one shape for the adjacent ranges of a run). `Cityscape.registerDecorationStyle` gives a style to a class name, so Monaco's class names keep working. The styles travel through Monaco's rendering as class names (`ViewLineRenderer` is unchanged) and are resolved when painting. When several styles apply to a part of a line, each property is resolved like the CSS cascade of Monaco's style sheets, not by the order of the class names on the part (Monaco orders them by decoration end offset): a style with `important: true` (CSS `!important`) wins over the others, then the highest `priority` (0 by default), then the style registered last (the order of rules in a style sheet; registering a class name again moves it last), typed styles given to decorations coming after the registered ones, in the order of their decorations on the part. The token classes of the theme come first, like Monaco's token style sheet. `letterSpacing` is accepted and not applied yet. Tests: `CityscapeEditorTest.testTypedDecorationsRender`, `testRegisteredClassStyle`, `testDecorationStyleCascade`.
- **Hidden text inside a line.** `hidden: true` hides the range of a decoration, `replacement` (injected text options) shows a text in its place, and `revealOnCursorLine` shows the text again on the lines that have a cursor. Each view hides through its line projections: the hidden text is an injection that replaces `replacedLength` characters (`InjectedTextOptions.replacedLength`, generalizing Monaco's injected text), merged with the injections of the model, so positions inside the range map to its start and the cursor moves over it. Each editor reveals on its own cursor lines. Monaco's whole line hidden areas (`setHiddenAreas`) are unchanged. Tests: `ViewModelHiddenRangesTest`, `LineBreakDataTest` (hidden and replacement cases).
- **Wrapping indent per level.** loreline-monaco patches Monaco (`[loreline]`, `globalThis.__lorelineWrapExtraColumns`) so that the extra indent of continuation lines (`wrappingIndent` `indent` and `deepIndent`) is a number of columns per level instead of a tab stop. Cityscape takes it as an argument of the line breaks computers (`wrappingIndentColumns`, -1 for Monaco's behaviour), set per editor (`CityscapeEditor.wrappingIndentColumns`). Tests: `MonospaceLineBreaksComputerTest` (loreline cases).
- **Active line number on wrapped lines.** loreline-monaco's patch keeps the active line number color on the number of the cursor's model line when the cursor is on a continuation line; Cityscape does the same.
- **Measured line breaks.** The `advanced` wrapping strategy breaks lines where Glaze's text system measures them (`MeasuredLineBreaksComputer`), not where the browser breaks a hidden `div`. Break opportunities approximate CSS `overflow-wrap: break-word`: after spaces, around CJK ideographs and kana (unless `wordBreak` is `keepAll`), after a hyphen, and between graphemes when a word does not fit; trailing spaces hang. Unicode line breaking (UAX 14) is not implemented, so some breaks differ from a browser's. The `simple` strategy (monospace) is Monaco's. Tests: none against Monaco (the DOM breaks are not recorded).
- **Smooth scrolling by the kit.** `Scrollable.setScrollPositionSmooth` sets the position at once: smooth scrolling and scrollbar animations are the kit's (see "Chrome from the Glaze kit").
- **Selection shape.** Selections have rounded outer corners (3 px, like Monaco's `roundedSelection`), but the concave corners Monaco draws where two lines of a selection have different widths are square.

## Cursor and editing

- **Word segmentation without `Intl`.** With `wordSegmenterLocales` set, Monaco finds the words of CJK text with `Intl.Segmenter` (word granularity, ICU dictionaries). On JavaScript Cityscape uses the same native `Intl.Segmenter`. Other targets have no `Intl`: the words are the UAX #29 word boundaries of Glaze's `unicode_segmentation` (Unicode 17, the segments containing a letter or a number, `UnicodeWordIndices`), whatever the locale. UAX #29 has no dictionary, so a run of ideographs or hiragana is split per character where ICU finds words (`これ|は|テスト|です` with ICU, `こ|れ|は|テスト|で|す` with UAX #29); katakana runs and Latin words are the same. The locales are validated by `Intl.Segmenter.supportedLocalesOf` on JavaScript and kept when they are well formed BCP 47 tags elsewhere. Lines without the option are not affected (Monaco does not segment them either). Tests: `WordOperationsTest` (`Recognize words` tests on JavaScript, `testCityscapeRecognizeWordsUax29` on the other targets), `EditorOptionsTruthTest` (the `wordSegmenterLocales` cases `"true"` and `"false"`, unknown to ICU, are skipped on the other targets).
- **Grapheme rules.** Cursor moves and deletions use Monaco's own grapheme rules (`strings.ts` `GraphemeIterator`, its break table and its stateless pairwise rules, ported as they are: a run of regional indicators is one grapheme, no GB9c), not Glaze's UAX #29 segmentation: the cursor stops where Monaco's does. Tests: `StringsTest`, `EditorControllerCursorTest.testGraphemeBreaking`, the surrogate pair and emoji tests of `CursorTest`.
- **Sorting without `Intl`.** Monaco sorts lines (`editor.action.sortLinesAscending`, `sortLinesDescending`) with `new Intl.Collator().compare`. On JavaScript Cityscape uses the same native collator (`cityscape.base.common.Collator`). Other targets have no `Intl`: the comparison follows the three levels of the Unicode collation algorithm with a small table instead of ICU's data (base characters first: whitespace, punctuation and symbols, digits, letters without case or accent, Latin-1 and Latin Extended-A letters folded to their base letter; then accents; then case, lower case first). ASCII letters and digits sort like ICU's root collation; punctuation, ligatures (`æ`, `œ`, `ß`) and other scripts can sort differently. Tests: `SortLinesCommandTest`, `LinesOperationsTest` (`SortLinesAscendingActionTest`, `SortLinesDescendingActionTest`).

## Commands, keybindings and the editor API

- **Keys go through Glaze bindings.** Monaco listens to `keydown` on its text area and dispatches every key. Cityscape binds each chord used by a keybinding of the context as a Glaze key binding in the `CityscapeEditor` key context; the focused editor resolves it with Monaco's resolver against its context keys, and when no keybinding applies the key goes on to the bindings of the ancestors (`cx.propagate()`), so app shortcuts keep working around an editor. A binding of an ancestor never runs for a key the editor handles (the deepest context wins, like a DOM `preventDefault`). In chord mode, a key without a Glaze binding ends the chord, like Monaco. Tests: `CityscapeApiTest.testAppShortcutsInAnAncestorContext`, `testKeysGoToTheFocusedEditor`, `testChords`.
- **Chord mode timing and messages.** Monaco leaves chord mode after 5 seconds with a 500 ms timer, and when the window loses focus, and shows status messages ("(⌘K) was pressed. Waiting for second key of chord..."); Cityscape checks the 5 seconds at the next key and shows no message (no status bar). Single modifier keybindings (`shift shift`) are not dispatched: Glaze has no key up event for a lone modifier. Tests: `CityscapeApiTest.testChords`.
- **`addCommand` belongs to its editor.** Monaco's `editor.addCommand` registers a keybinding that is active in every editor of the page (its `when` clause has no editor condition). Cityscape adds `editorId == <id>` to its `when` clause, like `addAction` does for its precondition, and removes the command and keybinding when the editor is destroyed. Tests: `CityscapeApiTest.testAddCommandIsScopedToItsEditor`.
- **View state kept per model.** Monaco's standalone editor forgets the view state of a model when another model is set (hosts keep it with `saveViewState`/`restoreViewState`). A Cityscape editor keeps the view state (cursors, scroll, contributions such as folding) of each model it showed and restores it when the model comes back; `saveViewState`/`restoreViewState` still work. `ICodeEditorWidgetOptions.keepViewStatePerModel: false` gives Monaco's behaviour (the test editors use it). Tests: `CityscapeApiTest.testViewStateIsKeptPerModel`, `FoldingControllerTest.testFoldsAreKeptWhenTheModelComesBack`.
- **Cut, copy and paste keybindings always bound.** Monaco registers the keybindings of `editor.action.clipboardCutAction`, `CopyAction` and `PasteAction` only in Electron, and lets the browser's clipboard events do the work elsewhere. Cityscape has no browser events: they are always bound (Monaco's native keybindings) and run on the editor through `_executeClipboardAction`.
- **Tab never moves the focus.** Monaco's tab focus mode (`editor.action.toggleTabFocusMode`, Ctrl+M) is not ported: the `tabMovesFocus` context key stays false and Tab indents.
- **Trim trailing whitespace in strings and regular expressions.** Monaco's `editor.action.trimTrailingWhitespace` reads the setting `files.trimTrailingWhitespaceInRegexAndStrings` from its configuration service. Cityscape has no configuration service: the action uses the default value of the setting (true, whitespace is also trimmed inside strings and regular expressions). `TrimTrailingWhitespaceCommand` still takes the flag.
- **Contributions created without idle callbacks.** Monaco creates the contributions registered `AfterFirstRender` when the window is idle after the model is attached, and the `Eventually` ones in idle time later; Cityscape creates both when the model is attached. `Eager` is Monaco's; `BeforeFirstInteraction` ones are created before a mouse or key event like Monaco, and on the next turn of the app after the editor is created (Monaco's idle time), so that an editor typed into through its API alone has its suggest controller and quick suggestions (`LanguageFeaturesTest.asyncTestQuickSuggestionsWithoutInteraction`). `getContribution` creates a pending one at once in both.
- **Marker events are synchronous.** Monaco's marker service debounces `onMarkerChanged` (one event per turn of the event loop with the merged resources). Cityscape fires it during `changeOne`/`changeAll`/`remove`, so the squiggles follow `setModelMarkers` at once. Tests: `MarkerServiceTest.testChangeAllSendsEventForCleared`.
- **Markers of models outside the model service.** Monaco decorates the markers of the models of its model service only. Cityscape also decorates them on a model shown by an editor of the context that was not created through `Cityscape.createModel` (until the model is disposed). Tests: `CityscapeApiTest.testMarkersAreRenderedAsDecorations`.
- **Glaze key contexts see part of the context keys.** The editor's root publishes its context keys to Glaze (for bindings of the host written against `CityscapeEditor && editorTextFocus`) only when Glaze can express them: true booleans as identifiers, strings without dots as `key=value`. Monaco's own `when` clauses are always evaluated by Monaco's code against all the keys.
- **Localization by key or English text.** Monaco loads its translations as one array per module (indexed messages of a build). Cityscape's `context.nls` takes tables keyed by the message key or by its English text (the shape of community translation tables such as loreline-monaco's), the key winning when both exist. Tests: `CityscapeApiTest.testNlsTables`.

## Folding

- **Debounce of the folding update.** Monaco waits before computing the folding ranges after a change, with a delay that follows the time the last computations took (`ILanguageFeatureDebounceService`: a sliding average of 6, between 200 ms and 40 s, kept per model and providers in a global service, 300 ms at first). Cityscape uses the same rule per editor (`FoldingController`), reset when the model changes. Only the timing differs; the ranges and fold states are Monaco's. Tests call `_flushPendingUpdate` instead of waiting.
- **Folding controls drawn by the view.** Monaco's codicons (`codicon-folding-expanded`, `codicon-folding-collapsed` and the manual ones, classes kept on the decorations) are drawn from the outlines of the codicon glyphs (`chevron-down`, `chevron-right` of `codicon.ttf`, `cityscape.view.Codicons`) at 140% of the font size, `margin-left: 2px`, centered in the line decorations like folding.css, in `editorGutter.foldingControlForeground`; the size, stroke and position were measured on the real Monaco 0.52.2 at font size 14. The glyph's baseline is snapped to the device pixel like Monaco's text; Glaze rasterizes the outline, so the antialiasing differs slightly. With `showFoldingControls: 'mouseover'` the expanded chevrons appear at once when the mouse is over the gutter (Monaco fades them in over 0.5 s); the mouse cursor stays the editor's over them (Monaco shows a pointer). The `⋯` of `.inline-folded:after` is drawn after the text of the line in `editor.foldPlaceholderForeground`, and counts as text of the line for the mouse like Monaco's pseudo element. Tests: `FoldingControllerTest.testCollapsedLineShowsTheEllipsis`, the folding scene of tests/visual (`CITYSCAPE_VISUAL_SCENE=folding`).

## Find and replace

- **The find widget is built with the Glaze kit.** Monaco's `FindWidget` (DOM) is replaced by `FindWidget` (`cityscape/contrib/find/view`): kit `Input`s for the find and replace fields, kit buttons for the toggles (match case, whole word, regular expression, preserve case, find in selection) and the actions (previous, next, replace, replace all, close, toggle replace), and a label with Monaco's match count (`N of M`, `?` when the position is not known, `+` at the match limit, `No results`). It sits at the top right corner of the editor like Monaco's overlay widget and takes the colors of the VS Code theme of the editor (`editorWidget.*`, `input.*`, `inputOption.*`, `inputValidation.errorBorder`), else the kit theme's. Not ported: the search history of the inputs, the resizing sash, the extra space the widget adds above the first line (`find.addExtraSpaceOnTop` is accepted and ignored: the find widget does not add its view zone yet), the small `FindOptionsWidget` shown when an option is toggled from the keyboard while the widget is closed, the aria live messages, the validation message of an invalid regular expression (the input border turns red when there is no result). The state, the search, the decorations and the commands are Monaco's. Tests: `FindWidgetTest`.
- **Keys in the find widget.** The fields are single line kit inputs. In the find input Enter goes to the next match and Shift+Enter to the previous one; Cmd+Enter (Ctrl+Enter) goes to the next match too, where Monaco inserts a line break for a multi-line search. In the replace input Enter replaces one match and Cmd+Enter (Ctrl+Enter) replaces all, on every platform (Monaco binds Cmd+Enter on macOS only; loreline-monaco's fix does the same as Cityscape). Tab and Shift+Tab move between the two inputs only (Monaco also stops on the toggles and buttons). Escape closes the widget like Monaco. Tests: `FindWidgetTest`.
- **Global find clipboard.** The macOS find pasteboard (`find.globalFindClipboard`, the clipboard service's find text) is not ported: the option is accepted and has no effect. vscode's tests of it are commented out in vscode.
- **Go to match.** `editor.action.goToMatchFindAction` (a quick input asking for a match number) is not ported; `CommonFindController.goToMatch(index)` is.
- **Query options storage.** The find options (case, whole word, regular expression, preserve case) are kept like vscode's in a storage service, `Cityscape.storageService`, in memory for the life of the context by default (a host can set its own to persist them). A new find controller of the context starts with the last options, like vscode's workspace storage.
- **Find widget created with the editor.** Monaco creates the find widget when the find widget is first opened; Cityscape adds it with the find controller, and renders its Glaze view from the first render of the editor (hidden until the find widget opens), so that opening the widget renders the widget and not the editor. The behaviour is the same.

## Editing contributions

- **Bracket pair colorization per editor option.** Monaco's standalone editor writes the `bracketPairColorization` option to its configuration service, and the model service gives it to every model. Cityscape has no configuration service: an editor whose options set `bracketPairColorization` gives it to its model (`bracketColorizationOptions`); a model shown by several editors takes the last one set. The colors come from the theme like Monaco's theming participant: the levels cycle through the non transparent colors of `editorBracketHighlight.foreground1..6`, and `editorBracketHighlight.unexpectedBracket.foreground` colors the unexpected closing brackets. Tests: `BracketPairColorsTest`.
- **Balanced brackets of TextMate grammars.** VS Code gives a grammar contribution without `balancedBracketScopes` the default `['*']` (and `[]` for `unbalancedBracketScopes`); `TextMateService.registerGrammar` does the same, so the brackets of TextMate tokens count for the bracket pairs (colorization, matching, guides) outside strings, comments and regular expressions. This is VS Code's behaviour, noted here because Monaco's standalone editor (Monarch tokens) has no grammar contributions. Tests: `BracketPairColorsTest.testBracketDecorationsWithTextMateTokens`.
- **Guides painted by the view.** The guides of Monaco's `IndentGuidesOverlay` (indentation, bracket pairs, horizontal bracket guides, active guides) are computed by the same code (`IndentGuides.getGuidesByLine`) and painted as 1 pixel lines with the colors of its theming participant (`IndentGuideColors`). Tests: `BracketPairColorsTest.testGuideColorsOfTheTheme`.
- **Word highlighter state per context.** Monaco keeps the query of the word highlighter and the decoration ids of each model in statics of `WordHighlighter` (one page). Cityscape keeps them per `Cityscape` context (`WordHighlighterState`): editors of one context share them like Monaco's editors of one page, two contexts do not. Document highlight providers give their result to a callback (at once or later) and are asked in order of score until one answers (Monaco's `first`). The aria alerts of `moveNext`/`moveBack` are not ported. Tests: `WordHighlighterTest`.
- **Sticky scroll widget painted by Glaze.** The state of Monaco's sticky scroll (`findScrollWidgetState`, the candidates of the outline, folding and indentation models, the line to rebuild from) is ported; the widget is a Glaze view over the editor painting the lines as the view renders them (tokens and inline decorations), the line numbers, the folding codicons (16 px), the background, the bottom border and the shadow of stickyScroll.css. A click reveals the line, Shift+click the end of its scope, a click on a folding icon folds or unfolds; the keyboard focus of the widget (`editor.action.focusStickyScroll`, arrows, Enter, Escape) highlights the focused line. Not ported: the definition link gesture (Cmd+hover underline and Cmd+click to the definition, which needs the definition providers) and the context menu of the widget. `editor.action.toggleStickyScroll` toggles the option of the focused editor (Monaco writes the setting). The outline model is built by `OutlineModel.create` at each update (Monaco's `OutlineModelService` caches it; Cityscape has an `OutlineModelService` too, which the sticky scroll does not use yet). Tests: `StickyScrollTest`.
- **Indentation sizes without a quick pick.** `editor.action.indentUsingTabs`, `indentUsingSpaces` and `changeTabDisplaySize` take the size from their argument (a number, or `{tabSize: n}`, 1 to 8) instead of Monaco's quick pick; without a valid size they do nothing, like a dismissed pick. `editor.action.detectIndentation` uses the default creation options of the model service (there is no configuration service). Tests: `IndentationTest`.
- **In-place replace without a worker.** `editor.action.inPlaceReplace.up`/`down` compute the next value of the value set synchronously (`EditorSimpleWorker.navigateValueSet`), instead of asking the editor worker service; there is no `EditorState` check of the editor after the request.
- **Smart select.** The bracket selection ranges are computed in one call (Monaco yields between rounds with `setTimeout`; its round limit and the resulting ranges are kept). `SmartSelectController.run` and `SmartSelect.provideSelectionRanges` call back instead of returning promises. The `_executeSelectionRangeProvider` command is not ported (no `ITextModelService`). Tests: `SmartSelectTest`.
- **Multicursor announcements.** The aria status messages of the multicursor actions (`announceCursorChange`) are not ported. Tests: `MulticursorTest`.

## Language features

- **Providers answer through callbacks.** Monaco's providers return a value or a promise (`ProviderResult<T>`); Cityscape's are Haxe interfaces whose methods give their result to a `resolve` callback, at once or later, and take Monaco's `CancellationToken`. Optional members of a provider (`resolveCompletionItem`, `resolveCodeAction`...) are nullable function fields. Inside the editor the results go through `cityscape.base.common.Promise`, which settles synchronously when the provider answers at once: tests run without waiting, and the order of the results is Monaco's. Tests: `SuggestModelTest`, `CodeActionTest`, `LanguageFeaturesTest`.
- **Popups built with the Glaze kit.** The suggest widget, the content hover, the quick fix menu and the lightbulb are overlay widgets whose Glaze views are anchored at the cursor or the hover position (the kit's `Positioner`, flipped above when there is no room below like Monaco's content widgets; the hover is placed by `view/ContentWidgetPositioner.hx`, Monaco's own rules: `_findPositionPreference` with `hover.above` and `_layoutBoxInPage`, the window standing for Monaco's page). The suggest list and the hover take the colors of the editor's theme (`editorSuggestWidget.*`, `editorHoverWidget.*`, `textLink.foreground`), else the kit theme's; the quick fix menu is the kit's `PopupMenu` in the kit theme's colors (a host sets the kit theme mode to match its editor theme). Codicons are replaced by Lucide icons (`view/SymbolIcons.hx`). The visual scenes `suggest`, `hover` and `quickfix` of tests/visual show them in Dark+ and Light+.
- **Suggest widget.** Not ported: the resizing sash and the persisted size, the status bar, the explain mode, the aria announcements. The details of the focused item show in a side panel like Monaco's (toggled with Ctrl+Space). Tab completion's alternative suggestions (`insertNextSuggestion`, `insertPrevSuggestion`) and the scroll position kept around additional edits (`StableEditorScrollState`) are not ported. `suggest.localityBonus` has no effect: the word distance needs the bracket selection ranges and the word ranges of an editor worker, so `WordDistance.create` always gives `WordDistance.None` (Monaco's value without `localityBonus`). Inline completions are not ported, so the checks that suppress quick suggestions under an inline suggestion always allow them. Tests: `SuggestModelTest`, `CompletionModelTest`, `SuggestTest`.
- **Word based completions.** Monaco's `wordBasedSuggestions` setting (a global configuration value) is `Cityscape.wordBasedSuggestions` (`'off'`, `'currentDocument'`, `'matchingDocuments'`, the default, `'allDocuments'`). The words are computed in the editor's thread (Monaco asks its editor worker). Tests: `LanguageFeaturesTest`.
- **Hover.** The hover participants (Monaco's `HoverParticipantRegistry`, a global registry) are `Cityscape.hoverParticipants`: the markdown and the marker participants by default. The hover has Monaco's look and size (hover.css, hoverWidget.css, `ContentHoverWidget._updateMaxDimensions`): as wide and high as its content up to `max(0.66 × the editor's width, 500)` and `max(the editor's height / 4, 250)`, scrolling beyond with the kit's scrollbar, the editor's font size and line height, a line between the parts, the status bar with the keybindings of its actions (`View Problem (⌥F8)`). Markdown is not rendered by marked and the DOM: `MarkdownRenderer.parseHoverMarkdown` splits it into its top level blocks with the margins of hoverWidget.css (collapsed like CSS; `---` spans the hover), each rendered by the kit's `TextView` (inline code in `--monaco-monospace-font` on `textCodeBlock.background`, code blocks colored by the tokenizer of their language in the context). Of the HTML Monaco's sanitizer keeps (`supportHtml`), `<code>`, `<br>` and the formatting tags of the text view render, `<small>` renders smaller for the lines of a paragraph wholly in it (elsewhere its text keeps the paragraph's size: the text view has no per run size), the other tags are dropped and their text kept (a `<span style="color">` is not colored). Text selection stays within a block, and links are underlined in the kit's way (a hairline in the link color at 40%). A participant renders its parts at every frame the hover shows (Monaco renders them once): the status bar is the one of the first render, and the marker participant asks for quick fixes once per hover. `Cityscape.hoverChrome` lets a host restyle the surface of the hover (a style sheet in Monaco). Monaco tests whether the mouse left the editor over the hover from the DOM event; the hover is drawn above the editor here, so leaving the editor waits 50 ms to know whether the mouse went into the hover (`hover.sticky`). Not ported: focusing the hover (`editor.action.showHover` with focus), the verbosity actions, resizing the hover by hand. Tests: `LanguageFeaturesTest`, `HoverViewTest`, `HoverMarkdownTest`.
- **Lightbulb in the gutter.** Monaco places the lightbulb at the start of the line, or above, below or in the gutter when the text leaves no room; Cityscape always places it in the gutter of the cursor line (the glyph margin when shown, else the line decorations). A click on it shows the code actions. Tests: `LanguageFeaturesTest.testLightbulbOnTheLineOfAQuickFix`.
- **Code actions.** The quick fix menu lists the actions by group with a header per group, like Monaco's action widget; not ported: the action bar of the menu (documentation commands, show disabled), the preview of refactorings, the AI lightbulb. The refactor, source, organize imports, auto fix and fix all actions are not ported yet; Cmd+. (quick fix), the lightbulb and the quick fix of the marker hover are. `CodeActionContext` carries the markers of the range (`markers`) so that a provider (the LSP client) can give back the original diagnostics. A workspace edit is applied to the open models of the context; edits to other resources and file operations go to `Cityscape.workspaceEditHandler` (Monaco's bulk edit service). Tests: `CodeActionTest`, `CodeActionKeybindingResolverTest`, `LanguageFeaturesTest`.
- **Messages next to the cursor.** Monaco's `MessageController` (a message below the cursor such as "No definition found for 'x'" or "No code actions available") is not ported; the message and its position are given to `Cityscape.onNoResult`, for the host to show. Tests: `LanguageFeaturesTest`.
- **Go to error.** Monaco shows the marker of F8 (`editor.action.marker.nextInFiles`) and Alt+F8 (`editor.action.marker.next`) in a peek zone below its line. Cityscape moves the cursor to the marker like Monaco and shows the marker in the content hover, with its status bar (View Problem, Quick Fix...) and the position of the marker among the problems ("1 of 3 problems"). Markers of other models are visited through `openCodeEditor` like Monaco's. Escape closes it (`closeMarkersNavigation`). Tests: `LanguageFeaturesTest.testF8ShowsTheMarkerInTheHover`.
- **Go to definition.** F12 (`editor.action.revealDefinition`) goes to the first definition: the peek view is not ported, so `gotoLocation.multipleDefinitions` behaves as `'goto'`, and "go to next symbol" is not available. The location is opened with `CodeEditorService.openCodeEditor`: in the same editor when it is in its model, else by the handlers a host registers with `registerCodeEditorOpenHandler` (Monaco's standalone editor only opens locations of its own model). Cmd+hover (Ctrl+hover) underlines the definition link with the `goto-definition-link` decoration and shows the definition's first lines in the hover; Cmd+click goes to it. The declaration, type definition, implementation and references commands are not ported yet (their providers and `GoToSymbol` functions are). Tests: `LanguageFeaturesTest`.
- **Language server client.** `cityscape.lsp.LspClient` is new code (Monaco has none): it registers providers that turn Cityscape's requests into LSP requests over a transport (`InProcessTransport` for a server in the same process, or a host's own), and publishes diagnostics as markers. `registerProviders` (`false`, or the list of the server capabilities to register) lets a host keep the document sync, the diagnostics and `sendRequest` while it registers its own providers. Tests: `LspClientTest`, `LspConversionsTest`, `LanguageFeaturesTest` (with a fake in-process server).
- **Overlay widgets added after the first render.** The editor lists its overlay widgets when its component renders; the editor view is not a view of Glaze's dispatch tree, so adding or laying out an overlay widget also notifies the view that renders the `CityscapeEditor` component. Monaco adds the widget's DOM node at once. The behaviour is the same.

## Diff editor

- **Diff computed without a web worker.** Monaco computes the diff in its editor worker. Cityscape computes it on a background thread on the native targets (`ceramic.Runner.runInBackground`, the result applied on the main thread) and on the main thread on the web, at the next frame, in one go (no web worker for Haxe code yet), with Monaco's time limit (`maxComputationTime`) and 200 ms debounce after edits. Only the last computation started is applied (the worker answers in order in Monaco). The worker's cache of results (`WorkerBasedDocumentDiffProvider.diffCache`, ten entries shared by the page) is not ported. The diffs are Monaco's. Tests: `FixturesTest`, `DiffComputerTest`, `DiffEditorTest.asyncTestDiffComputedOffTheFrame`.
- **Deleted lines of the inline view are not wrapped.** Monaco renders the deleted lines of the inline view in view zones of the modified editor, wrapped with the modified editor's line breaks, from the tokens of the original model (`renderLines`). Cityscape paints them from the lines of the original editor as its view renders them (tokens and inline decorations), one view line per deleted line, with the `char-delete` ranges and the `delete-sign` codicons; `minWidthInPx` is 0. Tests: `DiffEditorTest.testInlineViewShowsTheDeletedLines`, the diff scene of tests/visual.
- **Bars of the hidden regions.** Monaco's `CollapsedCodeOverlayWidget` (a DOM overlay over a 24 px view zone) is painted by the zone (the `diffEditor.unchangedRegionBackground` bar, a 3 px shadow at its top and bottom approximating the inset `box-shadow`, the `unfold` codicon over the gutter, "N hidden lines" in the kit's UI font at 13 px). The edges are clicked, not dragged: a click on the top 4 px shows `revealLineCount` more lines above, on the bottom 6 px more lines below, a click on the codicon or a double click on the text all of them. The breadcrumbs of the bar and the `fold-unchanged` glyph margin codicon are not drawn (the click on the glyph margin of the first line of a revealed region collapses it). Tests: `DiffEditorTest.testHideUnchangedRegions`.
- **Not ported yet.** The gutter menu between the editors (`renderGutterMenu`), the revert arrows (`renderMarginRevertIcon`), the resizing sash (`enableSplitViewResizing`, the split stays at `splitViewDefaultRatio`), the moved code lines and comparison (`experimental.showMoves`: the moves are computed and decorated with Monaco's `movedOriginal`/`movedModified` block class names, which have no style), the accessible diff viewer, the true inline view (`experimental.useTrueInlineView`), the empty range markers (`diff-range-empty`, a 3 px border on an empty range), the box shadow and border between the side by side editors other than `diffEditor.border`, the accessibility signals of `goToDiff`, and the context keys of the diff editor other than `isInDiffLeftEditor` and `isInDiffRightEditor`.
- **Overview ruler.** The diff editor's overview ruler (30 px, the removed lines of the original on its left half, the inserted lines of the modified on its right half, the viewport) is painted by `CityscapeDiffEditor` from Monaco's `OverviewZoneManager` rules in logical pixels (Monaco rounds in device pixels). A click outside the viewport centers it on the pointer and drags it, like Monaco's delegated scrollbar pointer down; the mouse wheel over it is not forwarded.
