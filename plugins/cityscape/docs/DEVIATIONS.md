# Deviations from Monaco

Cityscape behaves like Monaco (vscode `src/vs/editor` at the commit of monaco-editor 0.52.2): expected values come from vscode's own tests, ported, or from recordings of the real Monaco, never from Cityscape. This file lists the intended differences, and only those. Each entry says what differs, why, and how it is tested.

Differences that only follow from Haxe (overloads merged into one method, static methods renamed with a `Static` suffix, `Event<void>` as `VoidEvent`...) are API conventions, described in [PORTING.md](PORTING.md); they change no behaviour and are not listed here.

## Decided in the plan, to be detailed as they are implemented

- **Rendering by Glaze instead of the DOM.** The view (`cityscape/view`) draws with Glaze; Monaco's DOM view parts are not ported.
- **Chrome from the Glaze kit.** Scrolling and scrollbars, popovers (hover, diagnostics), the suggest list, menus, the find widget and the color picker are the kit's, not Monaco's DOM widgets. Scroll positions are therefore not compared with recordings.
- **No minimap.** The `minimap` option and the minimap decorations are accepted and ignored.
- **Typed decoration style.** Decorations take a typed style (colors, font style, background, borders, joined ranges, hidden ranges) in addition to Monaco's CSS class names, which remain accepted as keys of registered styles.
- **Hidden text inside a line.** Monaco only hides whole lines; Cityscape can hide a range inside a line (through the line projections of the view model).
- **Per editor theme override.** The theme is global to a `Cityscape` context like Monaco's; an editor can override it.

## Option values

- **Options set to null.** Haxe has a single `null` where JavaScript has `undefined` and `null`: an option set to null is read as unset, so it takes its default. In Monaco a `null` reaches the validator (`readOnly: null` gives `false` there, the default `false` here too; `lineNumbers: null` gives `'off'` in Monaco and the default `'on'` here). Tests: `EditorOptionsTruthTest` (the Monaco truths do not include null inputs), `EditorConfigurationTest` (issues 94931 and 102920, where both agree).
- **Values of the wrong type copied as they are.** A few Monaco validators copy a value without checking its type (`gotoLocation.multipleDefinitions` and the other `multiple*` fields, `rulers[].color`). Cityscape keeps such a value only when it has the declared type (a string), and otherwise uses what Monaco uses for a missing value (`'peek'`, `null`). Values of the right type behave the same. Tests: `EditorOptionsTruthTest` (`gotoLocation`, `rulers` cases).

## Model

- **Regular expressions on the native targets.** Find (`TextModel.findMatches`, `TextModelSearch`) and word definitions use JavaScript regular expressions. On JavaScript they are the native `RegExp`. On hxcpp they run on PCRE2 10.42 (Haxe's `EReg`), with the source translated so that the JavaScript meaning is kept: `\w`, `\d`, `\b` are ASCII only, `\s` is JavaScript's set, `.` stops at `\n`, `\r`, U+2028 and U+2029, `^` and `$` follow JavaScript (also around `\r` with `m`), `\uXXXX`, `\u{...}`, `\v`, `\0`, `[]`, `[^]` and `\p{Script=...}` are supported. Differences left: a lookbehind of variable length is rejected by PCRE2 (the search then finds nothing, like an invalid pattern), a backreference to a group that did not take part fails instead of matching the empty string, lone surrogates in a pattern are rejected (in the searched text the result is undefined), case insensitive matching uses PCRE2's Unicode case folding. Tests: `RegExpTest` (JavaScript results, checked against the native `RegExp` by the Node run), `TextModelSearchTest` (all of vscode's cases pass on both targets).
- **Integer positions.** Line numbers, columns and offsets are `Int`: the NaN, float and `undefined` coordinates that Monaco's validation accepts (and floors) cannot be represented. vscode's tests for them are not ported (`EditorModelTextModelTest`, `TextModelCreateSnapshotTest`). On hxcpp, decoration offsets are 32 bit (Monaco's are 53 bit numbers): vscode's 'force delta overflow' interval tree test is not ported.
- **Undo without confirmation.** Monaco asks for a confirmation before undoing an element of another undo source or flagged `confirmBeforeUndo`; there is no dialog service here, the undo proceeds. Errors while undoing or redoing drop the stacks of the resource like Monaco's and go to `Errors.onUnexpectedError` (Monaco also shows a notification). Elements spanning several models (`MultiModelEditStackElement`, workspace elements) are not supported yet.

## Tokenization and themes

- **Background tokenization with a frame budget.** Monaco tokenizes the lines of a model attached to an editor in idle callbacks (`runWhenGlobalIdle`, until the idle deadline, yielding every 1 to 2 ms). Ceramic has no idle callback: the `BackgroundScheduler` of the `Cityscape` context runs the background tokenizers of all its models on the app's update event, with one time budget per frame shared by all of them (`budgetMs`, 4 ms by default), in turn. Which lines are tokenized, in which order, and the resulting tokens are Monaco's; only the timing differs. The visible lines are tokenized synchronously when an editor's visible range changes, like Monaco. Tests: `TextMateTruthTest.testBackgroundSchedulerTokenizesAttachedModels`, `asyncTestBackgroundTokenizationRunsInFrames`.
- **Registries per context.** Monaco's global `TokenizationRegistry`, `ModesRegistry` and language associations are fields of a `Cityscape` context (`tokenizationRegistry`, `modesRegistry`, `languageService`). Tokenizer factories resolve synchronously (`getOrCreate` returns the support instead of a promise). File name patterns (globs) of language associations are not supported yet.
- **Built-in theme rules are not changed by inheriting themes.** In Monaco, `StandaloneTheme.tokenTheme` appends the `editor.foreground`/`editor.background` rule of an inheriting theme to the rules array of the built-in base theme itself (`rules = baseData.rules; rules.push(rule)`), so the rule leaks into the next theme computed from the same base (a theme without `editor.foreground` then gets the foreground of another theme). Cityscape copies the array. Test: `StandaloneThemeServiceTest.testInheritedThemesDoNotChangeBuiltinData`.
- **TextMate token colors change live.** A theme with TextMate rules (`tokenColors` or tmTheme `settings`) sets the token color map of the context and retokenizes the models (visible lines at once, the rest in the background), like VS Code. loreline-monaco gives its theme to vscode-textmate once, so a theme change there only reaches the editor chrome; the tokens and colors for a given theme are the same. Test: `TextMateTruthTest.testLiveThemeChange`.
- **Language configuration from user settings.** Monaco's language configuration service also reads the settings `editor.language.brackets` and `editor.language.colorizedBracketPairs`; Cityscape has no configuration service: only the configurations registered with `languageConfigurationService.register` apply.

## View and rendering

- **Typed decoration style.** Next to Monaco's class names, `IModelDecorationOptions` takes typed styles: `inlineStyle` (like `inlineClassName`), `style` (like `className`), `lineStyle` (a whole line, like `className` with `isWholeLine`), `glyphMarginStyle`, `linesDecorationsStyle`, `lineNumberStyle`, `marginStyle`, and injected text takes `inlineStyle`. A style (`IDecorationStyle`) has a color, font style and weight, opacity, underline, strikethrough, font features, a background with a corner radius and vertical padding, a border, and `join` (one shape for the adjacent ranges of a run). `Cityscape.registerDecorationStyle` gives a style to a class name, so Monaco's class names keep working. The styles travel through Monaco's rendering as class names (`ViewLineRenderer` is unchanged) and are resolved when painting. `letterSpacing` is accepted and not applied yet. Tests: `CityscapeEditorTest.testTypedDecorationsRender`, `testRegisteredClassStyle`.
- **Hidden text inside a line.** `hidden: true` hides the range of a decoration, `replacement` (injected text options) shows a text in its place, and `revealOnCursorLine` shows the text again on the lines that have a cursor. Each view hides through its line projections: the hidden text is an injection that replaces `replacedLength` characters (`InjectedTextOptions.replacedLength`, generalizing Monaco's injected text), merged with the injections of the model, so positions inside the range map to its start and the cursor moves over it. Each editor reveals on its own cursor lines. Monaco's whole line hidden areas (`setHiddenAreas`) are unchanged. Tests: `ViewModelHiddenRangesTest`, `LineBreakDataTest` (hidden and replacement cases).
- **Wrapping indent per level.** loreline-monaco patches Monaco (`[loreline]`, `globalThis.__lorelineWrapExtraColumns`) so that the extra indent of continuation lines (`wrappingIndent` `indent` and `deepIndent`) is a number of columns per level instead of a tab stop. Cityscape takes it as an argument of the line breaks computers (`wrappingIndentColumns`, -1 for Monaco's behaviour), set per editor (`CityscapeEditor.wrappingIndentColumns`). Tests: `MonospaceLineBreaksComputerTest` (loreline cases).
- **Active line number on wrapped lines.** loreline-monaco's patch keeps the active line number color on the number of the cursor's model line when the cursor is on a continuation line; Cityscape does the same.
- **Measured line breaks.** The `advanced` wrapping strategy breaks lines where Glaze's text system measures them (`MeasuredLineBreaksComputer`), not where the browser breaks a hidden `div`. Break opportunities approximate CSS `overflow-wrap: break-word`: after spaces, around CJK ideographs and kana (unless `wordBreak` is `keepAll`), after a hyphen, and between graphemes when a word does not fit; trailing spaces hang. Unicode line breaking (UAX 14) is not implemented, so some breaks differ from a browser's. The `simple` strategy (monospace) is Monaco's. Tests: none against Monaco (the DOM breaks are not recorded).
- **Smooth scrolling by the kit.** `Scrollable.setScrollPositionSmooth` sets the position at once: smooth scrolling and scrollbar animations are the kit's (see "Chrome from the Glaze kit").
- **Selection shape.** Selections have rounded outer corners (3 px, like Monaco's `roundedSelection`), but the concave corners Monaco draws where two lines of a selection have different widths are square.

## Cursor and editing

- **Word segmentation without `Intl`.** With `wordSegmenterLocales` set, Monaco finds the words of CJK text with `Intl.Segmenter` (word granularity, ICU dictionaries). On JavaScript Cityscape uses the same native `Intl.Segmenter`. Other targets have no `Intl`: the words are the UAX #29 word boundaries of Glaze's `unicode_segmentation` (Unicode 17, the segments containing a letter or a number, `UnicodeWordIndices`), whatever the locale. UAX #29 has no dictionary, so a run of ideographs or hiragana is split per character where ICU finds words (`これ|は|テスト|です` with ICU, `こ|れ|は|テスト|で|す` with UAX #29); katakana runs and Latin words are the same. The locales are validated by `Intl.Segmenter.supportedLocalesOf` on JavaScript and kept when they are well formed BCP 47 tags elsewhere. Lines without the option are not affected (Monaco does not segment them either). Tests: `WordOperationsTest` (`Recognize words` tests on JavaScript, `testCityscapeRecognizeWordsUax29` on the other targets), `EditorOptionsTruthTest` (the `wordSegmenterLocales` cases `"true"` and `"false"`, unknown to ICU, are skipped on the other targets).
- **Grapheme rules.** Cursor moves and deletions use Monaco's own grapheme rules (`strings.ts` `GraphemeIterator`, its break table and its stateless pairwise rules, ported as they are: a run of regional indicators is one grapheme, no GB9c), not Glaze's UAX #29 segmentation: the cursor stops where Monaco's does. Tests: `StringsTest`, `EditorControllerCursorTest.testGraphemeBreaking`, the surrogate pair and emoji tests of `CursorTest`.

## Commands, keybindings and the editor API

- **Keys go through Glaze bindings.** Monaco listens to `keydown` on its text area and dispatches every key. Cityscape binds each chord used by a keybinding of the context as a Glaze key binding in the `CityscapeEditor` key context; the focused editor resolves it with Monaco's resolver against its context keys, and when no keybinding applies the key goes on to the bindings of the ancestors (`cx.propagate()`), so app shortcuts keep working around an editor. A binding of an ancestor never runs for a key the editor handles (the deepest context wins, like a DOM `preventDefault`). In chord mode, a key without a Glaze binding ends the chord, like Monaco. Tests: `CityscapeApiTest.testAppShortcutsInAnAncestorContext`, `testKeysGoToTheFocusedEditor`, `testChords`.
- **Chord mode timing and messages.** Monaco leaves chord mode after 5 seconds with a 500 ms timer, and when the window loses focus, and shows status messages ("(⌘K) was pressed. Waiting for second key of chord..."); Cityscape checks the 5 seconds at the next key and shows no message (no status bar). Single modifier keybindings (`shift shift`) are not dispatched: Glaze has no key up event for a lone modifier. Tests: `CityscapeApiTest.testChords`.
- **`addCommand` belongs to its editor.** Monaco's `editor.addCommand` registers a keybinding that is active in every editor of the page (its `when` clause has no editor condition). Cityscape adds `editorId == <id>` to its `when` clause, like `addAction` does for its precondition, and removes the command and keybinding when the editor is destroyed. Tests: `CityscapeApiTest.testAddCommandIsScopedToItsEditor`.
- **View state kept per model.** Monaco's standalone editor forgets the view state of a model when another model is set (hosts keep it with `saveViewState`/`restoreViewState`). A Cityscape editor keeps the view state (cursors, scroll, contributions such as folding) of each model it showed and restores it when the model comes back; `saveViewState`/`restoreViewState` still work. `ICodeEditorWidgetOptions.keepViewStatePerModel: false` gives Monaco's behaviour (the test editors use it). Tests: `CityscapeApiTest.testViewStateIsKeptPerModel`, `FoldingControllerTest.testFoldsAreKeptWhenTheModelComesBack`.
- **Cut, copy and paste keybindings always bound.** Monaco registers the keybindings of `editor.action.clipboardCutAction`, `CopyAction` and `PasteAction` only in Electron, and lets the browser's clipboard events do the work elsewhere. Cityscape has no browser events: they are always bound (Monaco's native keybindings) and run on the editor through `_executeClipboardAction`.
- **Tab never moves the focus.** Monaco's tab focus mode (`editor.action.toggleTabFocusMode`, Ctrl+M) is not ported: the `tabMovesFocus` context key stays false and Tab indents.
- **Contributions created without idle callbacks.** Monaco creates the contributions registered `AfterFirstRender` when the window is idle after the model is attached, and the `Eventually` ones in idle time later; Cityscape creates both when the model is attached. `Eager` and `BeforeFirstInteraction` are Monaco's, and `getContribution` creates a pending one at once in both.
- **Marker events are synchronous.** Monaco's marker service debounces `onMarkerChanged` (one event per turn of the event loop with the merged resources). Cityscape fires it during `changeOne`/`changeAll`/`remove`, so the squiggles follow `setModelMarkers` at once. Tests: `MarkerServiceTest.testChangeAllSendsEventForCleared`.
- **Markers of models outside the model service.** Monaco decorates the markers of the models of its model service only. Cityscape also decorates them on a model shown by an editor of the context that was not created through `Cityscape.createModel` (until the model is disposed). Tests: `CityscapeApiTest.testMarkersAreRenderedAsDecorations`.
- **Glaze key contexts see part of the context keys.** The editor's root publishes its context keys to Glaze (for bindings of the host written against `CityscapeEditor && editorTextFocus`) only when Glaze can express them: true booleans as identifiers, strings without dots as `key=value`. Monaco's own `when` clauses are always evaluated by Monaco's code against all the keys.
- **Localization by key or English text.** Monaco loads its translations as one array per module (indexed messages of a build). Cityscape's `context.nls` takes tables keyed by the message key or by its English text (the shape of community translation tables such as loreline-monaco's), the key winning when both exist. Tests: `CityscapeApiTest.testNlsTables`.

## Folding

- **Debounce of the folding update.** Monaco waits before computing the folding ranges after a change, with a delay that follows the time the last computations took (`ILanguageFeatureDebounceService`: a sliding average of 6, between 200 ms and 40 s, kept per model and providers in a global service, 300 ms at first). Cityscape uses the same rule per editor (`FoldingController`), reset when the model changes. Only the timing differs; the ranges and fold states are Monaco's. Tests call `_flushPendingUpdate` instead of waiting.
- **Folding controls drawn by the view.** Monaco's codicons (`codicon-folding-expanded`, `codicon-folding-collapsed` and the manual ones, classes kept on the decorations) are drawn as the kit's chevron icons (Lucide `chevron-down`, `chevron-right`, or what the kit theme maps them to), in `editorGutter.foldingControlForeground`, centered in the line decorations like folding.css. With `showFoldingControls: 'mouseover'` the expanded chevrons appear at once when the mouse is over the gutter (Monaco fades them in over 0.5 s); the mouse cursor stays the editor's over them (Monaco shows a pointer). The `⋯` of `.inline-folded:after` is drawn after the text of the line in `editor.foldPlaceholderForeground`, and counts as text of the line for the mouse like Monaco's pseudo element. Tests: `FoldingControllerTest.testCollapsedLineShowsTheEllipsis`, the folding scene of tests/visual (`CITYSCAPE_VISUAL_SCENE=folding`).
