# Deviations from Monaco

Cityscape behaves like Monaco (vscode `src/vs/editor` at the commit of monaco-editor 0.52.2): expected values come from vscode's own tests, ported, or from recordings of the real Monaco, never from Cityscape. This file lists the intended differences, and only those. Each entry says what differs, why, and how it is tested.

Differences that only follow from Haxe (overloads merged into one method, static methods renamed with a `Static` suffix, `Event<void>` as `VoidEvent`...) are API conventions, described in [PORTING.md](PORTING.md); they change no behaviour and are not listed here.

## Decided in the plan, to be detailed as they are implemented

- **Rendering by Glaze instead of the DOM.** The view (`cityscape/view`) draws with Glaze; Monaco's DOM view parts are not ported.
- **Chrome from the Glaze kit.** Scrolling and scrollbars, popovers (hover, diagnostics), the suggest list, menus, the find widget and the color picker are the kit's, not Monaco's DOM widgets. Scroll positions are therefore not compared with recordings.
- **No minimap.** The `minimap` option and the minimap decorations are accepted and ignored.
- **Typed decoration style.** Decorations take a typed style (colors, font style, background, borders, joined ranges, hidden ranges) in addition to Monaco's CSS class names, which remain accepted as keys of registered styles.
- **Hidden text inside a line.** Monaco only hides whole lines; Cityscape can hide a range inside a line (through the line projections of the view model).
- **Per editor theme override.** The theme is global to a `Cityscape` context like Monaco's; an editor can override it.

## Option values

- **Default font family (owner decision, 2026-11-10).** When the host gives no `fontFamily` (option or prop), `CityscapeEditor` uses JetBrains Mono, the monospace font bundled with Glaze (`CityscapeEditor.DEFAULT_FONT_FAMILY`), on every target, so that the web, native and Unity builds render the same text (the web cannot read the system's font files). Monaco's default list (`Menlo, Monaco, 'Courier New', monospace` on macOS, `Consolas, 'Courier New', monospace` on Windows) is not Cityscape's default; system fonts are used when the host asks for them (`fontFamily: 'Menlo, monospace'`). `EditorOptions` keeps vscode's default (its ported tests read it), and `CityscapeEditor` sets the bundled font with Monaco's other standalone defaults. Tests: `EditorFontsTest.testDefaultFontIsTheBundledMonospaceFont` (and `testGutterLayoutAtFontSize14`, which asks for Monaco's default font to compare with the recording).
- **Bracket features off by default (owner choice: quieter default, 2026-11-11).** An editor whose host does not give them has no bracket pair colors and no matching bracket boxes: `CityscapeEditor` sets `bracketPairColorization.enabled` to false when the host leaves it out (Monaco: true, `EDITOR_MODEL_DEFAULTS`; the other fields of the option are kept as given) and `matchBrackets` to `'never'` (Monaco: `'always'`). The bracket pair guides are off in Monaco already (`guides.bracketPairs: false`; `bracketPairsHorizontal: 'active'` and `highlightActiveBracketPair: true` only act when `bracketPairs` is on) and stay so. A host that gives the options gets Monaco's behaviour (`bracketPairColorization: {enabled: true}`, `matchBrackets: 'always'`, `guides: {bracketPairs: true}`). Like the default font, these defaults belong to `CityscapeEditor`: `EditorOptions` and `TextModelDefaults` keep vscode's values, read by the ported tests and the option truths of the real Monaco. The editor gives its colorization option to its model (`CodeEditorWidget._applyBracketPairColorization`); the model service gives the configuration's colorization to its models only when that setting changed, so that another model option of the configuration (an editor's tab size) does not undo the editor's (in Monaco the configuration is the only source of this model option: same behaviour). Tests: `BracketDefaultsTest`.
- **Options set to null.** Haxe has a single `null` where JavaScript has `undefined` and `null`: an option set to null is read as unset, so it takes its default. In Monaco a `null` reaches the validator (`readOnly: null` gives `false` there, the default `false` here too; `lineNumbers: null` gives `'off'` in Monaco and the default `'on'` here). Tests: `EditorOptionsTruthTest` (the Monaco truths do not include null inputs), `EditorConfigurationTest` (issues 94931 and 102920, where both agree).
- **Values of the wrong type copied as they are.** A few Monaco validators copy a value without checking its type (`gotoLocation.multipleDefinitions` and the other `multiple*` fields, `rulers[].color`). Cityscape keeps such a value only when it has the declared type (a string), and otherwise uses what Monaco uses for a missing value (`'peek'`, `null`). Values of the right type behave the same. Tests: `EditorOptionsTruthTest` (`gotoLocation`, `rulers` cases).

## Model

- **Regular expressions on the native targets.** Find (`TextModel.findMatches`, `TextModelSearch`) and word definitions use JavaScript regular expressions. On JavaScript they are the native `RegExp`. On hxcpp they run on PCRE2 10.42 (Haxe's `EReg`), with the source translated so that the JavaScript meaning is kept: `\w`, `\d`, `\b` are ASCII only, `\s` is JavaScript's set, `.` stops at `\n`, `\r`, U+2028 and U+2029, `^` and `$` follow JavaScript (also around `\r` with `m`), `\uXXXX`, `\u{...}`, `\v`, `\0`, `[]`, `[^]` and `\p{Script=...}` are supported. Differences left: a lookbehind of variable length is rejected by PCRE2 (the search then finds nothing, like an invalid pattern), a backreference to a group that did not take part fails instead of matching the empty string, lone surrogates in a pattern are rejected (in the searched text the result is undefined), case insensitive matching uses PCRE2's Unicode case folding. Tests: `RegExpTest` (JavaScript results, checked against the native `RegExp` by the Node run), `TextModelSearchTest` (all of vscode's cases pass on both targets).
- **Integer positions.** Line numbers, columns and offsets are `Int`: the NaN, float and `undefined` coordinates that Monaco's validation accepts (and floors) cannot be represented. vscode's tests for them are not ported (`EditorModelTextModelTest`, `TextModelCreateSnapshotTest`). On hxcpp, decoration offsets are 32 bit (Monaco's are 53 bit numbers): vscode's 'force delta overflow' interval tree test is not ported.
- **Undo without confirmation.** Monaco asks for a confirmation before undoing an element of another undo source or flagged `confirmBeforeUndo`; there is no dialog service here, the undo proceeds. Errors while undoing or redoing drop the stacks of the resource like Monaco's and go to `Errors.onUnexpectedError` (Monaco also shows a notification). Elements spanning several models (`MultiModelEditStackElement`, workspace elements) are not supported yet.

## Options added by Cityscape

- **`scrollBeyondLastLineGap` (addition).** `{viewportFraction, minLines}`: when `scrollBeyondLastLine` is on, the space past the last line is `max(viewportFraction * viewport, minLines * lineHeight)`, the viewport being the editor height without its top and bottom padding (the exact laid out height: Monaco's layout height is an integer). It is gpui-kit's rule (`TextElement::empty_bottom_height`, `{viewportFraction: 0.5, minLines: 3}`, applied whether the text fits or not). Null by default: Monaco's space (one viewport less a line) is unchanged. Option id 151 (after Monaco's ids). Tests: `CityscapeEditorTest.testScrollBeyondLastLineGapAndThumbPadding`.
- **`scrollbarThumbExcludesPadding` (addition).** The kit scrollbar measures its vertical thumb against the viewport and the content without the top and bottom padding (the scroll handle tells it, `ScrollbarThumbPadding`), like the scrollbar of gpui-kit's editors, whose padding is outside the scrolled text; with `scrollBeyondLastLineGap` the content height given to the scrollbar is the exact one (Monaco's scroll state keeps integers). The track and the scroll range are unchanged. False by default. Option id 152. The kit inspector of Glaze uses both, so that its style panes scroll like gpui-kit's editor did.
- **`preferColorEmoji` (addition, owner decision 2026-11-11).** True by default: every emoji (Unicode's `Extended_Pictographic`: `☕`, `☂` with or without U+FE0F, `❤`, `✌`, `☺`, `©`...) is drawn with the color emoji font on every target, natively and on the web alike, even when a font of `fontFamily` (Menlo, the editor's font) has a monochrome text glyph for it; U+FE0E after it asks for the text presentation. Chromium follows the font list there (`☕` is Menlo's text glyph in loreline-monaco): the owner prefers real emoji everywhere. The other characters (CJK, symbols that are not emoji) keep the font list fallbacks. `preferColorEmoji: false` gives the browser's order back (a listed font's text glyph first, the emoji font for what the list lacks). It sets Glaze's `Font.preferColorEmoji` on the editor fonts (plain Glaze keeps GPUI's rules). Changing it at run time renders the lines again; the line breaks computed before keep their widths until the text or the layout changes. Option id 153. Tests: `EditorFontsTest.testFontListFallbacksBeforeTheSystemFonts`, Glaze's `BundledEmojiFontTest.testPreferColorEmojiDrawsEveryEmojiInColor` and `CanvasFallbackTest.testPreferColorEmojiAndFontListOnTheWeb`.
- **`overviewRulerPosition` and `overviewRulerGap` (additions).** `overviewRulerPosition: 'beside'` puts the decorations overview ruler in its own column left of the vertical scrollbar, `overviewRulerGap` pixels apart (0 by default, clamped to 0..1000), so its marks and the kit scrollbar's thumb do not overlap; `'overlay'` (the default, any other value too) is Monaco's ruler under the scrollbar. loreline-monaco does the same with its style sheet (`.decorationsOverviewRuler { right: scrollbarSize + 2px }`, its `verticalScrollbarSize`): only the ruler moves, so the layout stays Monaco's (content width, viewport and wrapping columns unchanged) and the ruler is drawn over the right of the text area, like there. `layoutInfo` keeps Monaco's values (`overviewRuler.right` 0), the view reads the placement (`EditorViewOptions.OverviewRulerPlacement`); the ruler fills `editorOverviewRuler.background` when the theme has it (Monaco's ruler does too); the column is a scrollbar target for the mouse (Monaco's `_hitTestScrollbar` for the ruler, a child of the scrollable element), and sticky scroll stops at the ruler (loreline-monaco gives the sticky widget `right: scrollbarSize + 11px`, 1 px over the ruler's border, a rounding of its own the option does not copy). Option ids 154 and 155. Tests: `EditorFontsTest.testOverviewRulerBesideTheScrollbar`, and loreline-cityscape's J2 comparison.
- **`scrollbar.trackColor`, `scrollbar.thumbColor` and `scrollbar.thumbRadius` (additions, owner decision 2026-11-11: the line backgrounds stop at the scrollbar track).** Monaco's vertical scrollbar is transparent: the current line highlight, the whole line decorations, the selections and the text go on under it to the editor's right edge. In Cityscape the track is opaque by default: the band of `scrollbar.verticalScrollbarSize` (`layoutInfo.verticalScrollbarWidth`) is filled with `editor.background` over the text and the line backgrounds, under the scrollable element's shadows, the overview ruler and the kit scrollbar's thumb, so the ruler's marks stay visible where Monaco's ruler lies (under the scrollbar). With `overviewRulerPosition: 'beside'` the ruler's column and `overviewRulerGap` are part of the track (loreline-monaco gives the moved ruler the track's background). `trackColor` gives another color (`#rgb`, `#rrggbb`, `#rrggbbaa`, `rgb()`, `rgba()`); `'transparent'` is Monaco's scrollbar, and a value that is not a color is the default. `thumbColor` (the same in every state: normal, hovered, dragged) and `thumbRadius` (0 to 1000 pixels, at most half the thumb's width) style the kit thumb, the kit's look when they are not given. These are the editor scrollbar settings of loreline-monaco's `scrollbar` option (main.js `updateScrollbarStyle`: `.scrollbar.vertical { background-color: trackColor }`, `.slider { border-radius: thumbRadius; background-color: thumbColor }`; its `scrollbarSize` is Monaco's `verticalScrollbarSize` and `verticalSliderSize`); the scrollbars of the popups (hover, suggest list, parameter hints) keep the kit's look. They are fields of Monaco's `scrollbar` option, validated with it (a color is a non empty string, the radius a number; anything else is the default). The horizontal scrollbar is not drawn by Cityscape. Glaze's kit inspector gives `trackColor: 'transparent'` (gpui-kit's scrollbar lies over the text). Tests: `ScrollbarTrackTest`.
- **`overflowWidgetsBounds` (addition, owner decision 2026-11-10).** Where the widgets anchored in the text are placed: `'window'` (the default, any other value too) is Monaco's, whose content widgets with `allowEditorOverflow` (suggestions, hover, parameter hints, rename input, color picker) choose their side and their height in the page (`document.body`, the window here) and may cover what is around the editor; `'editor'` puts the editor's bounds in place of the window in the same rules (`_layoutBoxInPage` with its 22 pixel clearances, the suggest widget's `_layout` and `_placeAtAnchor`, `_findPositionPreference` with its 30 and 24 pixels), caps the hover and the parameter hints to the room on the larger side, keeps every box inside the editor (over the line when its side is too small) and clips what is still larger. The quick fix menu then goes below the line, else above, in the editor, at most half the editor high (450 pixels at most, the kit's rule with the editor for the window) and scrolls. The references peek view is a view zone inside the editor and is not concerned. Placement: `ContentWidgetAnchors.page` (`EditorWidgets.overflowPage`). Option id 156. Tests: `OverflowWidgetsBoundsTest` (both values: suggestions and their details, hover, quick fix menu, the positioner, the validation).

## Tokenization and themes

- **Background tokenization with a frame budget.** Monaco tokenizes the lines of a model attached to an editor in idle callbacks (`runWhenGlobalIdle`, until the idle deadline, yielding every 1 to 2 ms). Ceramic has no idle callback: the `BackgroundScheduler` of the `Cityscape` context runs the background tokenizers of all its models on the app's update event, with one time budget per frame shared by all of them (`budgetMs`, 4 ms by default), in turn. Which lines are tokenized, in which order, and the resulting tokens are Monaco's; only the timing differs. The visible lines are tokenized synchronously when an editor's visible range changes, like Monaco. Tests: `TextMateTruthTest.testBackgroundSchedulerTokenizesAttachedModels`, `asyncTestBackgroundTokenizationRunsInFrames`.
- **Registries per context.** Monaco's global `TokenizationRegistry`, `ModesRegistry` and language associations are fields of a `Cityscape` context (`tokenizationRegistry`, `modesRegistry`, `languageService`). Tokenizer factories resolve synchronously (`getOrCreate` returns the support instead of a promise). File name patterns (globs) of language associations are not supported yet.
- **Built-in theme rules are not changed by inheriting themes.** In Monaco, `StandaloneTheme.tokenTheme` appends the `editor.foreground`/`editor.background` rule of an inheriting theme to the rules array of the built-in base theme itself (`rules = baseData.rules; rules.push(rule)`), so the rule leaks into the next theme computed from the same base (a theme without `editor.foreground` then gets the foreground of another theme). Cityscape copies the array. Test: `StandaloneThemeServiceTest.testInheritedThemesDoNotChangeBuiltinData`.
- **TextMate token colors change live.** A theme with TextMate rules (`tokenColors` or tmTheme `settings`) sets the token color map of the context and retokenizes the models (visible lines at once, the rest in the background), like VS Code. loreline-monaco gives its theme to vscode-textmate once, so a theme change there only reaches the editor chrome; the tokens and colors for a given theme are the same. Test: `TextMateTruthTest.testLiveThemeChange`.
- **Themes and grammars of the host (additions).** `VSCodeDefaultThemes` gives VS Code's Dark+ and Light+ (Monaco only has `vs` and `vs-dark`, whose rules are for Monarch tokens); `kit/KitTheme` makes a theme of the Glaze kit theme's colors and maps the TextMate scopes to the kit's highlight names like the kit's highlighter; `kit/KitGrammars` registers the TextMate grammars bundled with Glaze. Nothing of Monaco changes.
- **Language configuration from user settings.** Monaco's language configuration service also reads the settings `editor.language.brackets` and `editor.language.colorizedBracketPairs`; Cityscape has no configuration service: only the configurations registered with `languageConfigurationService.register` apply.

## View and rendering

- **Editor fonts like a browser.** The `fontFamily` option is a CSS list: the first family added or installed is the editor's font, the others (those available, and the generic families, `monospace` being Menlo on macOS) are its fallbacks, tried in order for the characters it lacks before the fonts of the system; emoji go to the color emoji font (`preferColorEmoji`, above), and with `preferColorEmoji: false` `'Maple Mono', monospace` draws `☕` with Menlo's text glyph, like Chromium. On the web, the graphemes the browser draws for an editor font (CJK, emoji) are measured as whole runs, so the kerning between them applies like Chromium's (Glaze's canvas fallback for `Font.wholeRunShaping`). The lines are shaped whole like Chromium (`Font.wholeRunShaping`), not word by word like GPUI: Hiragino Sans's kerning of `って` and `こう` applies (kana come from Hiragino Sans, the kana font of Glaze's system fallback). The kit's vertical scrollbar fills the band `scrollbar.verticalScrollbarSize` leaves in the layout, its thumb no wider than `verticalSliderSize` (the kit's thumb in its own 16 px band). Tests: `EditorFontsTest.testFontListFallbacksBeforeTheSystemFonts`, `EditorFontsTest.testLigaturesReachTheShaper`.
- **Typed decoration style.** Next to Monaco's class names, `IModelDecorationOptions` takes typed styles: `inlineStyle` (like `inlineClassName`), `style` (like `className`), `lineStyle` (a whole line, like `className` with `isWholeLine`), `glyphMarginStyle`, `linesDecorationsStyle`, `lineNumberStyle`, `marginStyle`, and injected text takes `inlineStyle`. A style (`IDecorationStyle`) has a color, font style and weight, opacity, underline, strikethrough, font features, a background with a corner radius and vertical padding, a border, and `join` (one shape for the adjacent ranges of a run). `Cityscape.registerDecorationStyle` gives a style to a class name, so Monaco's class names keep working. The styles travel through Monaco's rendering as class names (`ViewLineRenderer` is unchanged) and are resolved when painting. When several styles apply to a part of a line, each property is resolved like the CSS cascade of Monaco's style sheets, not by the order of the class names on the part (Monaco orders them by decoration end offset): a style with `important: true` (CSS `!important`) wins over the others, then the highest `priority` (0 by default), then the style registered last (the order of rules in a style sheet; registering a class name again moves it last), typed styles given to decorations coming after the registered ones, in the order of their decorations on the part. The token classes of the theme come first, like Monaco's token style sheet. `letterSpacing` is accepted and not applied yet. Tests: `CityscapeEditorTest.testTypedDecorationsRender`, `testRegisteredClassStyle`, `testDecorationStyleCascade`.
- **Hidden text inside a line.** `hidden: true` hides the range of a decoration, `replacement` (injected text options) shows a text in its place, and `revealOnCursorLine` shows the text again on the lines that have a cursor. Each view hides through its line projections: the hidden text is an injection that replaces `replacedLength` characters (`InjectedTextOptions.replacedLength`, generalizing Monaco's injected text), merged with the injections of the model, so positions inside the range map to its start and the cursor moves over it. Each editor reveals on its own cursor lines. Monaco's whole line hidden areas (`setHiddenAreas`) are unchanged. Tests: `ViewModelHiddenRangesTest`, `LineBreakDataTest` (hidden and replacement cases).
- **Wrapping indent per level.** loreline-monaco patches Monaco (`[loreline]`, `globalThis.__lorelineWrapExtraColumns`) so that the extra indent of continuation lines (`wrappingIndent` `indent` and `deepIndent`) is a number of columns per level instead of a tab stop. Cityscape takes it as an argument of the line breaks computers (`wrappingIndentColumns`, -1 for Monaco's behaviour), set per editor (`CityscapeEditor.wrappingIndentColumns`). Tests: `MonospaceLineBreaksComputerTest` (loreline cases).
- **Active line number on wrapped lines.** loreline-monaco's patch keeps the active line number color on the number of the cursor's model line when the cursor is on a continuation line; Cityscape does the same.
- **Measured line breaks.** The `advanced` wrapping strategy breaks lines where Glaze's text system measures them (`MeasuredLineBreaksComputer`), not where the browser breaks a hidden `div`. Break opportunities approximate CSS `overflow-wrap: break-word`: after spaces, around CJK ideographs and kana (unless `wordBreak` is `keepAll`), after a hyphen, and between graphemes when a word does not fit; trailing spaces hang. Unicode line breaking (UAX 14) is not implemented, so some breaks differ from a browser's. The `simple` strategy (monospace) is Monaco's. Tests: none against Monaco (the DOM breaks are not recorded).
- **Smooth scrolling by the kit.** `Scrollable.setScrollPositionSmooth` sets the position at once: smooth scrolling and scrollbar animations are the kit's (see "Chrome from the Glaze kit").
- **Selection shape.** Selections have rounded outer corners (3 px, like Monaco's `roundedSelection`), but the concave corners Monaco draws where two lines of a selection have different widths are square.

## Cursor and editing

- **Word segmentation without `Intl`.** With `wordSegmenterLocales` set, Monaco finds the words of CJK text with `Intl.Segmenter` (word granularity, ICU dictionaries). On JavaScript Cityscape uses the same native `Intl.Segmenter`. Other targets have no `Intl`: the words are the UAX #29 word boundaries of Glaze's `unicode_segmentation` (Unicode 17, the segments containing a letter or a number, `UnicodeWordIndices`), whatever the locale. UAX #29 has no dictionary, so a run of ideographs or hiragana is split per character where ICU finds words (`これ|は|テスト|です` with ICU, `こ|れ|は|テスト|で|す` with UAX #29); katakana runs and Latin words are the same. The locales are validated by `Intl.Segmenter.supportedLocalesOf` on JavaScript and kept when they are well formed BCP 47 tags elsewhere. Lines without the option are not affected (Monaco does not segment them either). Tests: `WordOperationsTest` (`Recognize words` tests on JavaScript, `testCityscapeRecognizeWordsUax29` on the other targets), `EditorOptionsTruthTest` (the `wordSegmenterLocales` cases `"true"` and `"false"`, unknown to ICU, are skipped on the other targets).
- **Grapheme rules.** Cursor moves and deletions use Monaco's own grapheme rules (`strings.ts` `GraphemeIterator`, its break table and its stateless pairwise rules, ported as they are: a run of regional indicators is one grapheme, no GB9c), not Glaze's UAX #29 segmentation: the cursor stops where Monaco's does. Tests: `StringsTest`, `EditorControllerCursorTest.testGraphemeBreaking`, the surrogate pair and emoji tests of `CursorTest`.
- **Sorting without `Intl`.** Monaco sorts lines (`editor.action.sortLinesAscending`, `sortLinesDescending`) with `new Intl.Collator().compare`. On JavaScript Cityscape uses the same native collator (`cityscape.base.common.Collator`). Other targets have no `Intl`: the comparison follows the three levels of the Unicode collation algorithm with a small table instead of ICU's data (base characters first: whitespace, punctuation and symbols, digits, letters without case or accent, Latin-1 and Latin Extended-A letters folded to their base letter; then accents; then case, lower case first). ASCII letters and digits sort like ICU's root collation; punctuation, ligatures (`æ`, `œ`, `ß`) and other scripts can sort differently. Tests: `SortLinesCommandTest`, `LinesOperationsTest` (`SortLinesAscendingActionTest`, `SortLinesDescendingActionTest`).

## Commands, keybindings and the editor API

- **Keys go through Glaze bindings.** Monaco listens to `keydown` on its text area and dispatches every key. Cityscape binds each chord used by a keybinding of the context as a Glaze key binding in the `CityscapeEditor` key context; the focused editor resolves it with Monaco's resolver against its context keys, and when no keybinding applies the key goes on to the bindings of the ancestors (`cx.propagate()`), so app shortcuts keep working around an editor. A binding of an ancestor never runs for a key the editor handles (the deepest context wins, like a DOM `preventDefault`). In chord mode, a key without a Glaze binding ends the chord, like Monaco. Tests: `CityscapeApiTest.testAppShortcutsInAnAncestorContext`, `testKeysGoToTheFocusedEditor`, `testChords`.
- **Chord mode timing and messages.** Monaco leaves chord mode after 5 seconds with a 500 ms timer, and when the window loses focus, and shows status messages ("(⌘K) was pressed. Waiting for second key of chord..."); Cityscape checks the 5 seconds at the next key and shows no message (no status bar). Single modifier keybindings (`shift shift`) are not dispatched: Glaze has no key up event for a lone modifier. Tests: `CityscapeApiTest.testChords`.
- **`addCommand` belongs to its editor.** Monaco's `editor.addCommand` registers a keybinding that is active in every editor of the page (its `when` clause has no editor condition). Cityscape adds `editorId == <id>` to its `when` clause, like `addAction` does for its precondition, and removes the command and keybinding when the editor is destroyed. Tests: `CityscapeApiTest.testAddCommandIsScopedToItsEditor`.
- **View state kept per model.** Monaco's standalone editor forgets the view state of a model when another model is set (hosts keep it with `saveViewState`/`restoreViewState`). A Cityscape editor keeps the view state (cursors, scroll, contributions such as folding) of each model it showed and restores it when the model comes back; `saveViewState`/`restoreViewState` still work. `ICodeEditorWidgetOptions.keepViewStatePerModel: false` gives Monaco's behaviour (the test editors use it). Tests: `CityscapeApiTest.testViewStateIsKeptPerModel`, `FoldingControllerTest.testFoldsAreKeptWhenTheModelComesBack`.
- **Cut, copy and paste keybindings always bound.** Monaco registers the keybindings of `editor.action.clipboardCutAction`, `CopyAction` and `PasteAction` only in Electron, and lets the browser's clipboard events do the work elsewhere. Cityscape has no browser events: they are always bound (Monaco's native keybindings) and run on the editor through `_executeClipboardAction`.
- **Tab never moves the focus.** Monaco's tab focus mode (`editor.action.toggleTabFocusMode`, Ctrl+M) is not ported: the `tabMovesFocus` context key stays false and Tab indents.
- **Trim trailing whitespace in strings and regular expressions.** Monaco's `editor.action.trimTrailingWhitespace` reads the setting `files.trimTrailingWhitespaceInRegexAndStrings` from its configuration service. Cityscape has no configuration service: the action uses the default value of the setting (true, whitespace is also trimmed inside strings and regular expressions). `TrimTrailingWhitespaceCommand` still takes the flag.
- **Contributions created without idle callbacks.** Monaco creates the contributions registered `AfterFirstRender` when the window is idle after the model is attached, and the `Eventually` ones in idle time later; Cityscape creates both when the model is attached. `Eager` is Monaco's; `BeforeFirstInteraction` ones are created before a mouse or key event like Monaco, and on the next turn of the app after the editor is created (Monaco's idle time), so that an editor typed into through its API alone has its suggest controller and quick suggestions (`LanguageFeaturesTest.asyncTestQuickSuggestionsWithoutInteraction`). `getContribution` creates a pending one at once in both.
- **Marker events are synchronous.** Monaco's marker service debounces `onMarkerChanged` (one event per turn of the event loop with the merged resources). Cityscape fires it during `changeOne`/`changeAll`/`remove`, so the squiggles follow `setModelMarkers` at once. Tests: `MarkerServiceTest.testChangeAllSendsEventForCleared`.
- **Markers of models outside the model service.** Monaco decorates the markers of the models of its model service only. Cityscape also decorates them on a model shown by an editor of the context that was not created through `Cityscape.createModel` (until the model is disposed). Tests: `CityscapeApiTest.testMarkersAreRenderedAsDecorations`.
- **Glaze key contexts see part of the context keys.** The editor's root publishes its context keys to Glaze (for bindings of the host written against `CityscapeEditor && editorTextFocus`) only when Glaze can express them: true booleans as identifiers, strings without dots as `key=value`. Monaco's own `when` clauses are always evaluated by Monaco's code against all the keys.
- **Localization by key or English text.** Monaco loads its translations as one array per module (indexed messages of a build). Cityscape's `context.nls` takes tables keyed by the message key or by its English text (the shape of community translation tables such as loreline-monaco's), the key winning when both exist. Tests: `CityscapeApiTest.testNlsTables`.

## Folding

- **Debounce of the folding update.** Monaco waits before computing the folding ranges after a change, with a delay that follows the time the last computations took (`ILanguageFeatureDebounceService`: a sliding average of 6, between 200 ms and 40 s, kept per model and providers in a global service, 300 ms at first). Cityscape uses the same rule per editor (`FoldingController`), reset when the model changes. Only the timing differs; the ranges and fold states are Monaco's. Tests call `_flushPendingUpdate` instead of waiting.
- **Folding controls drawn by the view.** Monaco's codicons (`codicon-folding-expanded`, `codicon-folding-collapsed` and the manual ones, classes kept on the decorations) are drawn from the outlines of the codicon glyphs (`chevron-down`, `chevron-right` of `codicon.ttf`, `cityscape.view.Codicons`) at 140% of the font size, `margin-left: 2px`, centered in the line decorations like folding.css, in `editorGutter.foldingControlForeground`; the size, stroke and position were measured on the real Monaco 0.52.2 at font size 14. The glyph's baseline is snapped to the device pixel like Monaco's text; Glaze rasterizes the outline, so the antialiasing differs slightly. With `showFoldingControls: 'mouseover'` the expanded chevrons appear at once when the mouse is over the gutter (Monaco fades them in over 0.5 s); the mouse cursor over them is Monaco's pointer. The `⋯` of `.inline-folded:after` is drawn after the text of the line in `editor.foldPlaceholderForeground`, and counts as text of the line for the mouse like Monaco's pseudo element, with Monaco's pointer over the glyph (the width of `⋯` after its 0.2em margin, by the ascent and descent of the font, measured on the real Monaco 0.52.2). Tests: `FoldingControllerTest.testCollapsedLineShowsTheEllipsis`, `MouseCursorTest`, the folding scene of tests/visual (`CITYSCAPE_VISUAL_SCENE=folding`).

## Find and replace

- **The find widget is built with the Glaze kit.** Monaco's `FindWidget` (DOM) is replaced by `FindWidget` (`cityscape/contrib/find/view`): kit `Input`s for the find and replace fields, kit buttons for the toggles (match case, whole word, regular expression, preserve case, find in selection) and the actions (previous, next, replace, replace all, close, toggle replace), and a label with Monaco's match count (`N of M`, `?` when the position is not known, `+` at the match limit, `No results`). It sits at the top right corner of the editor like Monaco's overlay widget and takes the colors of the VS Code theme of the editor (`editorWidget.*`, `input.*`, `inputOption.*`, `inputValidation.errorBorder`), else the kit theme's. The placeholders of the inputs are in `input.placeholderForeground` (VS Code's workbench rule; standalone Monaco 0.52.2 has no rule for them, so the browser's default gray shows, `#757575` in Chromium, and loreline-monaco injects its own color). Not ported: the search history of the inputs, the resizing sash, the extra space the widget adds above the first line (`find.addExtraSpaceOnTop` is accepted and ignored: the find widget does not add its view zone yet), the small `FindOptionsWidget` shown when an option is toggled from the keyboard while the widget is closed, the aria live messages, the validation message of an invalid regular expression (the input border turns red when there is no result). The state, the search, the decorations and the commands are Monaco's. Tests: `FindWidgetTest`.
- **Keys in the find widget.** The fields are single line kit inputs. In the find input Enter goes to the next match and Shift+Enter to the previous one; Cmd+Enter (Ctrl+Enter) goes to the next match too, where Monaco inserts a line break for a multi-line search. In the replace input Enter replaces one match and Cmd+Enter (Ctrl+Enter) replaces all, on every platform (Monaco binds Cmd+Enter on macOS only; loreline-monaco's fix does the same as Cityscape). Tab and Shift+Tab move between the two inputs only (Monaco also stops on the toggles and buttons). Escape closes the widget like Monaco. Tests: `FindWidgetTest`.
- **Global find clipboard.** The macOS find pasteboard (`find.globalFindClipboard`, the clipboard service's find text) is not ported: the option is accepted and has no effect. vscode's tests of it are commented out in vscode.
- **Go to match.** `editor.action.goToMatchFindAction` (a quick input asking for a match number) is not ported; `CommonFindController.goToMatch(index)` is.
- **Query options storage.** The find options (case, whole word, regular expression, preserve case) are kept like vscode's in a storage service, `Cityscape.storageService`, in memory for the life of the context by default (a host can set its own to persist them). A new find controller of the context starts with the last options, like vscode's workspace storage.
- **Find widget created with the editor.** Monaco creates the find widget when the find widget is first opened; Cityscape adds it with the find controller, and renders its Glaze view from the first render of the editor (hidden until the find widget opens), so that opening the widget renders the widget and not the editor. The behaviour is the same.

## Editing contributions

- **Drag and drop of the selection.** Monaco's dnd contribution (`dragAndDrop`, on by default) is ported: a single press on the text of the primary selection (not read only, no column selection, no Alt) starts a drag instead of moving the cursor, the target shows as Monaco's `dnd-target` (a 2 px dotted caret, black, `#AEAFAD` on dark themes, white on high contrast dark, painted by the view), the release moves the text there, or copies it with Alt on macOS (Ctrl elsewhere, the `copy` pointer), and Escape cancels. `mouseStyle` (`text`, `default`, `copy`) sets the pointer over the whole editor, not only over the text. Not ported: the drop of text or files from outside the editor and the paste and drop providers (`dropIntoEditor`, `pasteAs`). Tests: `CityscapeEditorTest.testDragAndDropOfTheSelection`.
- **Bracket pair colorization per editor option.** Monaco's standalone editor writes the `bracketPairColorization` option to its configuration service, and the model service gives it to every model. Cityscape has no configuration service: an editor whose options set `bracketPairColorization` gives it to its model (`bracketColorizationOptions`); a model shown by several editors takes the last one set. The colors come from the theme like Monaco's theming participant: the levels cycle through the non transparent colors of `editorBracketHighlight.foreground1..6`, and `editorBracketHighlight.unexpectedBracket.foreground` colors the unexpected closing brackets. Tests: `BracketPairColorsTest`.
- **Balanced brackets of TextMate grammars.** VS Code gives a grammar contribution without `balancedBracketScopes` the default `['*']` (and `[]` for `unbalancedBracketScopes`); `TextMateService.registerGrammar` does the same, so the brackets of TextMate tokens count for the bracket pairs (colorization, matching, guides) outside strings, comments and regular expressions. This is VS Code's behaviour, noted here because Monaco's standalone editor (Monarch tokens) has no grammar contributions. Tests: `BracketPairColorsTest.testBracketDecorationsWithTextMateTokens`.
- **Guides painted by the view.** The guides of Monaco's `IndentGuidesOverlay` (indentation, bracket pairs, horizontal bracket guides, active guides) are computed by the same code (`IndentGuides.getGuidesByLine`) and painted as 1 pixel lines with the colors of its theming participant (`IndentGuideColors`). Tests: `BracketPairColorsTest.testGuideColorsOfTheTheme`.
- **Word highlighter state per context.** Monaco keeps the query of the word highlighter and the decoration ids of each model in statics of `WordHighlighter` (one page). Cityscape keeps them per `Cityscape` context (`WordHighlighterState`): editors of one context share them like Monaco's editors of one page, two contexts do not. Document highlight providers give their result to a callback (at once or later) and are asked in order of score until one answers (Monaco's `first`). The aria alerts of `moveNext`/`moveBack` are not ported. Tests: `WordHighlighterTest`.
- **Scrollable element shadows.** `scrollbar.useShadows` (on by default) draws Monaco's inset shadows of scrollbars.css with Glaze's inset shadows: 3 px at the top of the text area when it is scrolled down, 3 px at its left when it is scrolled right, and the corner, in `scrollbar.shadow`, above the text and under the sticky scroll widget. Monaco places them over its scrollable element, whose scrollbars are DOM nodes under them; the kit scrollbar is painted after the text area, so the top shadow is under the kit's thumb. Test: `CityscapeEditorTest.testScrollShadows`.
- **Sticky scroll widget painted by Glaze.** The state of Monaco's sticky scroll (`findScrollWidgetState`, the candidates of the outline, folding and indentation models, the line to rebuild from) is ported; the widget is a Glaze view over the editor painting the lines as the view renders them (tokens and inline decorations), the line numbers, the folding codicons (16 px), the background, the bottom border and the shadow of stickyScroll.css (`box-shadow: 0 4px 2px -2px` in `editorStickyScroll.shadow`, a Glaze drop shadow). The mouse cursors are Monaco's: the pointer over the line contents and a folding icon shown, the arrow over the number column, the text cursor over the digits of a number (Chrome's `cursor: auto` over selectable text; its box here is the width of the number by the ascent and descent of the font, where the digits are drawn, Monaco's inline block is 2 pixels lower). A click reveals the line, Shift+click the end of its scope, a click on a folding icon folds or unfolds; the keyboard focus of the widget (`editor.action.focusStickyScroll`, arrows, Enter, Escape) highlights the focused line. Not ported: the definition link gesture (Cmd+hover underline and Cmd+click to the definition, which needs the definition providers) and the context menu of the widget. `editor.action.toggleStickyScroll` toggles the option of the focused editor (Monaco writes the setting). The outline model is built by `OutlineModel.create` at each update (Monaco's `OutlineModelService` caches it; Cityscape has an `OutlineModelService` too, which the sticky scroll does not use yet). Tests: `StickyScrollTest`.
- **Indentation sizes without a quick pick.** `editor.action.indentUsingTabs`, `indentUsingSpaces` and `changeTabDisplaySize` take the size from their argument (a number, or `{tabSize: n}`, 1 to 8) instead of Monaco's quick pick; without a valid size they do nothing, like a dismissed pick. `editor.action.detectIndentation` uses the default creation options of the model service (there is no configuration service). Tests: `IndentationTest`.
- **In-place replace without a worker.** `editor.action.inPlaceReplace.up`/`down` compute the next value of the value set synchronously (`EditorSimpleWorker.navigateValueSet`), instead of asking the editor worker service; there is no `EditorState` check of the editor after the request.
- **Smart select.** The bracket selection ranges are computed in one call (Monaco yields between rounds with `setTimeout`; its round limit and the resulting ranges are kept). `SmartSelectController.run` and `SmartSelect.provideSelectionRanges` call back instead of returning promises. The `_executeSelectionRangeProvider` command is not ported (no `ITextModelService`). Tests: `SmartSelectTest`.
- **Multicursor announcements.** The aria status messages of the multicursor actions (`announceCursorChange`) are not ported. Tests: `MulticursorTest`.

## Language features

- **Providers answer through callbacks.** Monaco's providers return a value or a promise (`ProviderResult<T>`); Cityscape's are Haxe interfaces whose methods give their result to a `resolve` callback, at once or later, and take Monaco's `CancellationToken`. Optional members of a provider (`resolveCompletionItem`, `resolveCodeAction`...) are nullable function fields. Inside the editor the results go through `cityscape.base.common.Promise`, which settles synchronously when the provider answers at once: tests run without waiting, and the order of the results is Monaco's. Tests: `SuggestModelTest`, `CodeActionTest`, `LanguageFeaturesTest`.
- **Popups built with the Glaze kit.** The suggest widget, the content hover, the quick fix menu and the lightbulb are overlay widgets whose Glaze views are anchored at the cursor or the hover position. The suggest widget, the hover, the parameter hints and the rename input are placed by `view/ContentWidgetPositioner.hx`, Monaco's own rules (`_layoutBoxInPage`, the window standing for Monaco's page, or the editor with `overflowWidgetsBounds: 'editor'`; the hover's side by `_findPositionPreference` with `hover.above`, the suggest widget's side and height by its `_layout`: below the cursor when the list fits there, else above, capped to the room on that side with 22 pixels of clearance, its details by `_placeAtAnchor`). The quick fix menu is the kit's `PopupMenu` placed by the kit's `Positioner` (below the line, flipped above when there is no room, kept in the window like Monaco's context view, or by `ContentWidgetPositioner` inside the editor with `overflowWidgetsBounds: 'editor'`; its height is the kit's, at most half the window or 450 pixels, where Monaco's action list takes at most 70% of the window). The suggest list and the hover take the colors of the editor's theme (`editorSuggestWidget.*`, `editorHoverWidget.*`, `textLink.foreground`), else the kit theme's; the quick fix menu is the kit's `PopupMenu` in the kit theme's colors (a host sets the kit theme mode to match its editor theme). The kind icons of the suggest list are Monaco's codicons, drawn from the outlines of `codicon.ttf` (`view/CodiconOutlines.hx`) at 16 px in the `symbolIcon.*Foreground` colors of symbolIcons.ts (`editorSuggestWidget.selectedIconForeground` in the focused row); so are the lightbulb and the icons of the quick fix menu (16 px: `light-bulb` in `editorLightBulb.foreground` for the quick fixes and the actions of no group, the group's `wrench`, `surround-with`, `symbol-file` or the AI `sparkle` in the row's color, in a row of the kit's menu). The scrollbars of the suggest list, the hover, the parameter hints, the quick fix menu (when it scrolls) and the peek tree are the kit's scrollbar with the look of Monaco's widget scrollbars: a 10 pixel square slider filling its track in `scrollbarSlider.background`, `hoverBackground` under the mouse and `activeBackground` while dragged (scrollbars.css, measured on the real Monaco 0.52.2), at least 20 pixels long; when they show and hide stays the kit's (the theme's scrollbar mode, and its scrollbar appearance: a quick fade in place by default; Monaco shows them while the mouse is over the widget and fades them out). The suggest list scrolls by whole rows, so its slider moves by rows. The visual scenes `suggest`, `hover` and `quickfix` of tests/visual show them in Dark+ and Light+.
- **Suggest widget.** Not ported: the resizing sash and the persisted size, the status bar, the explain mode, the aria announcements, the 2 pixel border of high contrast themes. The list scrolls by whole rows (Monaco's list by pixels): the rows of a capped list show from the first visible one, the last one cut. Tests of the size and side: `SuggestViewTest`. The details of the focused item show in a side panel like Monaco's (toggled with Ctrl+Space). Tab completion's alternative suggestions (`insertNextSuggestion`, `insertPrevSuggestion`) and the scroll position kept around additional edits (`StableEditorScrollState`) are not ported. `suggest.localityBonus` has no effect: the word distance needs the bracket selection ranges and the word ranges of an editor worker, so `WordDistance.create` always gives `WordDistance.None` (Monaco's value without `localityBonus`). Quick suggestions and trigger characters are suppressed under an inline suggestion like Monaco (`canShowQuickSuggest`, with the `inlineSuggestionVisible` and `inlineSuggestionSuppressSuggestions` context keys and `inlineSuggest.suppressSuggestions`). Tests: `SuggestModelTest`, `CompletionModelTest`, `SuggestTest`.
- **Word based completions.** Monaco's `wordBasedSuggestions` setting (a global configuration value) is `Cityscape.wordBasedSuggestions` (`'off'`, `'currentDocument'`, `'matchingDocuments'`, the default, `'allDocuments'`). The words are computed in the editor's thread (Monaco asks its editor worker); like the worker's mirror models, the words of each line are kept between requests and only the lines changed since the last one are scanned again (`textualSuggestCached`, same result as Monaco's `$textualSuggest`). Tests: `LanguageFeaturesTest`, `WordBasedCompletionsTest`.
- **Hover.** The hover participants (Monaco's `HoverParticipantRegistry`, a global registry) are `Cityscape.hoverParticipants`: the markdown and the marker participants by default. The hover has Monaco's look and size (hover.css, hoverWidget.css, `ContentHoverWidget._updateMaxDimensions`): as wide and high as its content up to `max(0.66 × the editor's width, 500)` and `max(the editor's height / 4, 250)`, scrolling beyond with the kit's scrollbar, the editor's font size and line height, a line between the parts, the status bar with the keybindings of its actions (`View Problem (⌥F8)`). Markdown is not rendered by marked and the DOM: `MarkdownRenderer.parseHoverMarkdown` splits it into its top level blocks with the margins of hoverWidget.css (collapsed like CSS; `---` spans the hover), each rendered by the kit's `TextView` (inline code in `--monaco-monospace-font` on `textCodeBlock.background`, code blocks colored by the tokenizer of their language in the context). Of the HTML Monaco's sanitizer keeps (`supportHtml`), `<code>`, `<br>` and the formatting tags of the text view render, `<small>` renders smaller for the lines of a paragraph wholly in it (elsewhere its text keeps the paragraph's size: the text view has no per run size), the other tags are dropped and their text kept (a `<span style="color">` is not colored). Text selection stays within a block, and links are underlined in the kit's way (a hairline in the link color at 40%). A participant renders its parts at every frame the hover shows (Monaco renders them once): the status bar is the one of the first render, and the marker participant asks for quick fixes once per hover. `Cityscape.hoverChrome` lets a host restyle the surface of the hover (a style sheet in Monaco). Monaco tests whether the mouse left the editor over the hover from the DOM event; the hover is drawn above the editor here, so leaving the editor waits 50 ms to know whether the mouse went into the hover (`hover.sticky`). Markdown with `supportThemeIcons` shows its `$(name)` icons as codicons at the size and in the color of the text (`MarkdownThemeIcons`: the icons become images the text view draws); Monaco rewrites the icons of the whole rendered HTML, code spans included, where Cityscape leaves the icons of code spans and code blocks as text. Not ported: focusing the hover (`editor.action.showHover` with focus), the verbosity actions, resizing the hover by hand. Tests: `LanguageFeaturesTest`, `HoverViewTest`, `HoverMarkdownTest`.
- **Lightbulb in the gutter.** Monaco places the lightbulb at the start of the line, or above, below or in the gutter when the text leaves no room; Cityscape always places it in the gutter of the cursor line (the glyph margin when shown, else the line decorations). Its codicon and color are Monaco's (`_updateLightBulbTitleAndIcon`, lightBulbWidget.css: `light-bulb`, `lightbulb-autofix` with a preferred quick fix, `lightbulb-sparkle` and `lightbulb-sparkle-autofix` with an AI fix, `sparkle-filled` when all are AI fixes; 16 px). A click on it shows the code actions. Tests: `LightBulbIconsTest`. Tests: `LanguageFeaturesTest.testLightbulbOnTheLineOfAQuickFix`.
- **Code actions.** The quick fix menu lists the actions by group with a header per group, like Monaco's action widget; not ported: the action bar of the menu (documentation commands, show disabled), the preview of refactorings, the AI lightbulb. The refactor, source, organize imports, auto fix and fix all actions are not ported yet; Cmd+. (quick fix), the lightbulb and the quick fix of the marker hover are. `CodeActionContext` carries the markers of the range (`markers`) so that a provider (the LSP client) can give back the original diagnostics. A workspace edit is applied to the open models of the context; edits to other resources and file operations go to `Cityscape.workspaceEditHandler` (Monaco's bulk edit service). Tests: `CodeActionTest`, `CodeActionKeybindingResolverTest`, `LanguageFeaturesTest`.
- **Messages next to the cursor.** Monaco's `MessageController` (a message below the cursor such as "No definition found for 'x'" or "No code actions available") is not ported; the message and its position are given to `Cityscape.onNoResult`, for the host to show. Tests: `LanguageFeaturesTest`.
- **Go to error.** Monaco shows the marker of F8 (`editor.action.marker.nextInFiles`) and Alt+F8 (`editor.action.marker.next`) in a peek zone below its line. Cityscape moves the cursor to the marker like Monaco and shows the marker in the content hover, with its status bar (View Problem, Quick Fix...) and the position of the marker among the problems ("1 of 3 problems"). Markers of other models are visited through `openCodeEditor` like Monaco's. Escape closes it (`closeMarkersNavigation`). Tests: `LanguageFeaturesTest.testF8ShowsTheMarkerInTheHover`.
- **Go to definition and the other symbol navigations.** goToCommands.ts is ported: go to and peek the definitions (F12, Alt+F12), declarations, type definitions, implementations (Cmd+F12, Cmd+Shift+F12) and references (Shift+F12, `editor.action.referenceSearch.trigger`), `editor.action.goToLocations`, `peekLocations`, `findReferences`, with Monaco's `gotoLocation` modes (`'peek'` by default with several results, `'gotoAndPeek'`, `'goto'` with F12 through the other locations, `editor.gotoNextSymbolFromResult`) and the alternative commands on the only result. Locations open with `CodeEditorService.openCodeEditor`: in the same editor when it is in its model, else by the handlers a host registers with `registerCodeEditorOpenHandler` (Monaco's standalone editor only opens locations of its own model); the side by side commands give `sideBySide` to the handlers. The "Symbol 1 of 3" status of `'goto'` mode goes to `Cityscape.onStatusMessage` (Monaco's notification service). Cmd+hover (Ctrl+hover) underlines the definition link with the `goto-definition-link` decoration and shows the definition's first lines in the hover; Cmd+click goes to it (or peeks it with `definitionLinkOpensInPeek`). Tests: `GoToCommandsTest`, `LanguageFeaturesTest`.
- **References peek view.** Monaco's peek view is a zone widget: a view zone pushes the lines below the reference down and the widget (head, preview editor, tree) sits in it, with an arrow on the column. Cityscape shows the same widget in a popup placed under the line like a content widget (above it when there is no room), as wide as the text area and as high as Monaco's zone (`heightInLines`, 18 lines by default, at most 80% of the editor; the head `ceil(lineHeight * 1.2)`), so the lines are not pushed and the popup does not scroll with them; no arrow, no resizing (the layout data is kept in the storage like Monaco's). The tree is a list in the kit's style with the rows of referencesTree.ts (file, folder, count badge; the line of each reference with its match highlighted by `peekViewResult.matchHighlightBackground`): Up and Down show the references, Enter (or a double click) goes to one, Ctrl/Cmd+Enter opens it to the side, Escape closes. The preview is a `CityscapeEditor` on the model of the reference, painted with `peekViewEditor.background` and `peekViewEditorGutter.background` (Monaco's CSS), with the `reference-decoration`s. The tree has no type navigation, no aria labels, and the previews read the models the context knows (Monaco resolves other files through its text model service; a file without model shows "no preview available"). Tests: `GoToCommandsTest`, `PeekViewTest`.
- **Language server client.** `cityscape.lsp.LspClient` is new code (Monaco has none): it registers providers that turn Cityscape's requests into LSP requests over a transport (`InProcessTransport` for a server in the same process, or a host's own), and publishes diagnostics as markers. It registers a provider for each feature the server declares, like vscode-languageclient (completion, hover, signature help, definition, declaration, type definition, implementation, references, document highlights, document symbols, code actions, code lenses, rename with `prepareRename`, formatting of documents, ranges and on type, folding ranges, selection ranges, inlay hints, semantic tokens full, delta and range, links, colors), with the conversions of its protocol converter and of vscode's extension host type converters (`LspConversions`); the `workspace/*/refresh` requests fire the providers' change events. `registerProviders` (`false`, or the list of the server capabilities to register) lets a host keep the document sync, the diagnostics and `sendRequest` while it registers its own providers. A server's commands keep their JSON arguments, except the VS Code commands Monaco registers with typed arguments (`editor.action.findReferences`, `editor.action.showReferences`, `editor.action.peekLocations`, `editor.action.goToLocations`): their uri, position and locations are converted to `Uri`, `Position` and `LocationLink`s (VS Code leaves that to the extensions' middleware). Tests: `LspClientTest`, `LspClientFeaturesTest`, `LspConversionsTest`, `LanguageFeaturesTest` (with a fake in-process server).
- **Overlay widgets added after the first render.** The editor lists its overlay widgets when its component renders; the editor view is not a view of Glaze's dispatch tree, so adding or laying out an overlay widget also notifies the view that renders the `CityscapeEditor` component. Monaco adds the widget's DOM node at once. The behaviour is the same.

## Diff editor

- **Diff computed without a web worker.** Monaco computes the diff in its editor worker. Cityscape computes it on a background thread on the native targets (`ceramic.Runner.runInBackground`, the result applied on the main thread) and on the main thread on the web, at the next frame, in one go (no web worker for Haxe code yet), with Monaco's time limit (`maxComputationTime`) and 200 ms debounce after edits. Only the last computation started is applied (the worker answers in order in Monaco). The worker's cache of results (`WorkerBasedDocumentDiffProvider.diffCache`, ten entries shared by the page) is not ported. The diffs are Monaco's. Tests: `FixturesTest`, `DiffComputerTest`, `DiffEditorTest.asyncTestDiffComputedOffTheFrame`.
- **Deleted lines of the inline view are not wrapped.** Monaco renders the deleted lines of the inline view in view zones of the modified editor, wrapped with the modified editor's line breaks, from the tokens of the original model (`renderLines`). Cityscape paints them from the lines of the original editor as its view renders them (tokens and inline decorations), one view line per deleted line, with the `char-delete` ranges and the `delete-sign` codicons; `minWidthInPx` is 0. Tests: `DiffEditorTest.testInlineViewShowsTheDeletedLines`, the diff scene of tests/visual.
- **Bars of the hidden regions.** Monaco's `CollapsedCodeOverlayWidget` (a DOM overlay over a 24 px view zone) is painted by the zone (the `diffEditor.unchangedRegionBackground` bar, a 3 px shadow at its top and bottom approximating the inset `box-shadow`, the `unfold` codicon over the gutter, "N hidden lines" in the kit's UI font at 13 px). The edges are clicked, not dragged: a click on the top 4 px shows `revealLineCount` more lines above, on the bottom 6 px more lines below, a click on the codicon or a double click on the text all of them. The breadcrumbs of the bar and the `fold-unchanged` glyph margin codicon are not drawn (the click on the glyph margin of the first line of a revealed region collapses it). Tests: `DiffEditorTest.testHideUnchangedRegions`.
- **Gutter menu.** The gutter menu between the editors (`renderGutterMenu`, Monaco's `DiffEditorGutter`, at the left of the inline view) is ported with the revert action of standalone Monaco ("Revert Block", the `arrow-right` codicon side by side, `discard` inline; "Revert Selection" for the changes the selections touch), drawn with Glaze: 35 pixels, a 20 by 18 pixel button per change placed by `DiffToolBar.layout`, `toolbar.hoverBackground` under the mouse, the pointer, the title as a kit tooltip. Its items show while the mouse is over the gutter and the change of the cursor always, at once (Monaco fades them in and out). Tests: `DiffEditorTest`.
- **Mouse cursors of the zones.** View zones have Monaco's arrow (they are outside the view lines), the deleted lines of the inline view the text cursor; the bars of the hidden regions have the cursors of style.css (`s-resize`, `n-resize` or `ns-resize` over the edges that show or hide lines, the pointer over the unfold codicon, the text cursor over "N hidden lines") over their own area (Monaco's `.top` and `.bottom` nodes reach 6 and 4 pixels beyond the bar). A zone gives its cursor through `IViewZone.mouseCursor` (a Cityscape addition). Tests: `DiffEditorTest`.
- **Not ported yet.** The revert arrows of the margin (`renderMarginRevertIcon`, used only when the gutter menu is off), the resizing sash (`enableSplitViewResizing`, the split stays at `splitViewDefaultRatio`), the moved code lines and comparison (`experimental.showMoves`: the moves are computed and decorated with Monaco's `movedOriginal`/`movedModified` block class names, which have no style), the accessible diff viewer, the true inline view (`experimental.useTrueInlineView`), the empty range markers (`diff-range-empty`, a 3 px border on an empty range), the box shadow and border between the side by side editors other than `diffEditor.border`, the accessibility signals of `goToDiff`, and the context keys of the diff editor other than `isInDiffLeftEditor` and `isInDiffRightEditor`.
- **Overview ruler.** The diff editor's overview ruler (30 px, the removed lines of the original on its left half, the inserted lines of the modified on its right half, the viewport) is painted by `CityscapeDiffEditor` from Monaco's `OverviewZoneManager` rules in logical pixels (Monaco rounds in device pixels). A click outside the viewport centers it on the pointer and drags it, like Monaco's delegated scrollbar pointer down; the mouse wheel over it is not forwarded.


## Links and colors

- **Default links and colors computed in place.** Monaco's editor worker service registers a link provider for every language (the default link computer, `$computeLinks`) and the default color provider computes CSS like colors (`$computeDefaultDocumentColors`) in its web worker; Cityscape registers the same providers per context (`LinksRegistration`, `ColorPickerRegistration`) and computes on the model itself, synchronously. The links and colors are Monaco's. The language feature debounce (`FeatureDebounceInformation`, 1 to 4 s for links, 1 s minimum for colors) is kept per contribution and model instead of a global service. Tests: `LinkComputerTest` (vscode's), `LinksTest`, `ColorPickerTest`.
- **Opening links.** Monaco's `IOpenerService` is `Cityscape.openerService`: the host's `Cityscape.openLink` is asked first (Monaco's contributed openers), then Monaco's default openers: `http`, `https` and `mailto` links open with Ceramic's `backend.openUrl` (the system browser, a new tab on the web, nothing when headless; Monaco uses `window.open`), `command:` links run their command with the arguments of their query, other links open through `codeEditorService.openCodeEditor` with the selection of their fragment. Monaco's notifications of a link that cannot open ("Failed to open this link because its target is missing.") go to `Cityscape.onNoResult`. The `_executeLinkProvider`, `_executeDocumentColorProvider` and `_executeColorPresentationProvider` commands are not ported (Cityscape's commands return nothing): `GetLinks.getLinks`, `ColorUtils.getColors` and `ColorUtils.findColorPresentations` are their bodies. Tests: `LinksTest`.
- **Color swatches.** Monaco's swatch (`colorpicker-color-decoration`) is an inline block of 0.8em with a border of 0.1em and margins of 0.1em 0.2em 0 0.2em, around its injected non breaking space. Cityscape's line layout gives injected text the width of its characters, so the swatch is the box of the non breaking space (the width of a space) made square by a negative vertical padding, centered on the text, with the color as background and a border of 0.1em (`#000`, `#eee` in dark themes); it has no margins, so it touches the text of the color. Monaco creates one CSS rule per color; Cityscape gives each swatch a typed style (`before.inlineStyle`), computed again when the theme or the font changes. Tests: `ColorPickerTest.testSwatchesOfTheDefaultColors`, the visual scene `RestLinksColorsVisualView`.
- **The color picker in a popover of its own.** Monaco shows the color picker in its content hover (the color hover participant). Cityscape shows it in a popover of its own next to the color (`ColorContribution`, placed like a content widget), with the colors of the hover: a click on a swatch (`colorDecoratorsActivatedOn` `'click'`, `'clickAndHover'`), the mouse resting on a swatch (`'hover'`, `'clickAndHover'`) or on the text of a color (`hover.enabled`, after `hover.delay`) opens it; Escape, a click elsewhere, a scroll or an edit made elsewhere close it, and one opened by the mouse resting closes when the mouse leaves the color. The header is Monaco's (the picked color with the label of its presentation, a click cycling through the presentations; the original color, a click going back to it) without the `color-mode` codicon and the checkerboard behind translucent colors. The body is the Glaze kit's color picker (its HSLA sliders, shown first, and its palette with the hex field) instead of Monaco's saturation box and hue and opacity strips. A palette or hex color, or the release of a slider, writes the color (Monaco writes on pointer up). The writing itself is Monaco's (`_updateEditorModel`: the presentation's `textEdit`, else its label over the color, its `additionalTextEdits`, an undo stop). Tests: `ColorPickerTest`.
- **Standalone color picker.** `editor.action.showOrFocusStandaloneColorPicker` shows the picker at the selection (the color of the editor containing it, else black with the default provider), `editor.action.insertColorWithStandaloneColorPicker` (Enter) writes the picked color and `editor.action.hideColorPicker` (Escape) or the close button of the header hides it. The picker does not take the keyboard focus (it counts as focused while it shows), has no Insert/Replace button and does not select the color found in the editor. Tests: `ColorPickerTest.testStandalonePickerInsertsTheColor`, `testStandalonePickerHides`.
- **Deprecated color setting.** `ColorDetector.isEnabled` does not read the deprecated `[languageId].colorDecorators.enable` setting (Cityscape has no language settings): only the `colorDecorators` option counts.
## Inlay hints and code lens

- **Font of the inlay hints.** Monaco shows the hints in the `inlayHints.fontSize` (when it is between 5 and the editor's size) and `inlayHints.fontFamily` of the option, vertically centered when they differ from the editor's. A Cityscape view line is shaped with one font size and family, so the hints use the editor's; the padding (`padding: 1px <fontSize / 4>px`, `border-radius: <fontSize / 4>px`) and the spacers (`fontSize / 3` wide) follow the editor's size too. The colors, backgrounds, padding, spacers, truncation (43 characters per line and an ellipsis) and the decorations are Monaco's. Tests: `InlayHintsTest`.
- **Horizontal padding and spacers by the view.** Monaco's CSS gives the label parts a horizontal padding and the spacers (a hair space) an inline-block width. Cityscape's typed styles take `paddingLeft`, `paddingRight` and `width` (injected text and inline styles): the view moves the shaped glyphs after the part and its box includes the padding (`RenderedViewLine.applyHorizontalSpacing`), so the cursor, the mouse and the boxes follow. The backgrounds of the parts of one hint are joined into one box with rounded outer corners (Monaco rounds the outer side of the first and last parts, the same look); two hints of the same kind side by side join too. Tests: `HorizontalSpacingTest`.
- **Ctrl+Alt of `onUnlessPressed` and `offUnlessPressed`.** Monaco listens to the modifier keys of the whole window (`ModifierKeyEmitter`); Cityscape follows the modifier keys the editor receives (the focused editor). Tests: `InlayHintsTest.testEnabledModes`.
- **Debounce of the requests.** Like the folding, the moving averages of `ILanguageFeatureDebounceService` (inlay hints: 25 ms minimum; code lens provide and resolve: 250 ms) are kept per controller and model instead of a global service. Only the timing differs; tests flush the schedulers (`InlayHintsController._flush`, `CodeLensContribution._flush`).
- **Go to the location of a hint part.** Cmd+click (Ctrl+click) on a part with a location runs the definition action at that location like Monaco (with the peek view when `definitionLinkOpensInPeek` is set). Monaco resolves the model of the location with its text model service; Cityscape asks the context's models, and opens a location in a model it does not know directly through `codeEditorService.openCodeEditor`. The context menu of such a part (`showGoToContextMenu`, right click) is not ported. The hovers of the providers at the location are asked on the models of the context only (Monaco resolves any resource with its text model service). Tests: `InlayHintsTest.testCmdClickOnALocationPartOpensIt`.
- **Errors of the commands.** Monaco notifies the error of a hint's or a lens's command (notification service, with the provider's name); Cityscape gives it to `Errors.onUnexpectedError`.
- **Code lenses painted by their view zone.** Monaco shows the lenses of a line in a content widget above the line, in the zone that reserves the space. Cityscape paints them in the zone (`CodeLensContentWidget.paint`): at the column of the first non whitespace character of the line, `editorCodeLens.foreground`, the `codeLensFontSize` (90% of the editor's size by default, Monaco's computation) in the `codeLensFontFamily` (the kit's UI font by default, Monaco's `.monaco-editor` font), ` | ` between the lenses, centered in the zone one pixel down (Monaco's `vertical-align: sub`). The `$(icon)` codicons of the titles (Monaco's `renderLabelWithIcons`, `Codicons.parseLabelWithIcons`) are drawn from the outlines of `codicon.ttf` at the lenses' font size, `vertical-align: middle` (half the x-height above the baseline), in the color of their link; a codicon without outline in `CodiconOutlines` is not drawn and takes no room. The `~spin` modifier does not spin. The fade-in is not ported, the tooltips of the lenses are not shown. A click on the zone finds the lens from the x of the mouse (Monaco's link element); the link under the mouse takes `editorLink.activeForeground` and the pointer. A zone counts as visible for the resolution when the line under it is in the visible ranges (Monaco reads the attribute its view sets on the zones it renders). Tests: `CodeLensTest`.
- **Formatting.** Only format on type is ported (formatActions.ts `FormatOnType`, the `formatOnType` option, `registerOnTypeFormattingEditProvider`); the format document and format selection actions and format on paste are not yet. Monaco's editor worker makes the edits more minimal before they are applied (`computeMoreMinimalEdits`, run synchronously on the model here). Tests: `LanguageFeaturesTest.testFormatOnType`.
- **Code lens cache storage.** Monaco stores the lines of the cached lenses (`codelens/cache2`) when the window closes; Cityscape reads them from the context's storage service when the cache is created and stores them when the host calls `context.codeLensCache.saveState()`. Tests: `CodeLensTest.testCacheIsStored`.
- **Not ported.** `codelens.showLensesInCurrentLine` (a quick pick of the commands of the cursor line: no quick input), the `_executeInlayHintProvider` and `_executeCodeLensProvider` commands (no `_execute*` command is ported), the accessibility of the hints (`getInlayHintsForLine` is ported, the accessible view is not).
## Snippets and parameter hints

- **Snippet placeholder boxes.** Monaco draws the placeholders of a snippet with a CSS outline (1 pixel outside the box, snippetSession.css) and gives the active ones a minimum width of 2 pixels, so an empty tab stop shows as a thin box. Cityscape draws the border inside the box of the text and paints an empty tab stop as a box of `minWidth` (4 pixels for `snippet-placeholder`, 2 for `finish-snippet-placeholder`, the width Monaco's outline gives), centered on its position. The colors are Monaco's (`editor.snippetTabstopHighlightBackground`/`Border`, `editor.snippetFinalTabstopHighlightBackground`/`Border`). Tests: `ParameterHintsEditorTest.testSnippetSessionThroughTheEditor` (the decorations and their style), the snippet hints scene of tests/visual.
- **Parameter hints widget built with Glaze.** Monaco's DOM widget (parameterHintsWidget.ts, parameterHints.css) is a Glaze view with its look: the hover colors, the editor's font size and line height, the signature in the editor's font with the active parameter in bold and `editorHoverWidget.highlightForeground`, the overload counter and chevrons when there are several signatures (Lucide chevrons for the codicons), the documentation with 8 pixel paragraph margins (collapsed like CSS), markdown rendered by the hover's renderer (`MarkdownRenderer.renderHoverMarkdown`), at most 440 pixels wide and `max(the editor's height / 4, 250)` high, scrolling with the kit's scrollbar. It is placed above the cursor, else below, like a content widget with `[ABOVE, BELOW]`, and follows the scroll. Not ported: the aria announcement of the active parameter, the `visible` class added 100 ms after showing (it has no style). Tests: `ParameterHintsEditorTest` (content, context keys, commands), the snippet hints scene of tests/visual.
- **Snippet paths are posix.** The file variables of snippets (`TM_FILENAME`, `TM_DIRECTORY`, `TM_FILEPATH`...) use the posix path functions on every target; Monaco uses the win32 ones for file paths on Windows. Tests: `SnippetVariablesTest` (vscode's `!isWindows` expectations).
## Inline completions

- **Additional lines of a ghost text painted by the view zone.** Monaco renders the lines of a ghost text after its first one with `renderViewLine` into the DOM node of a view zone (no token colors, `renderWhitespace: 'none'`, the editor's font). Cityscape's zone paints them with the editor's font: the `ghost-text` parts in `editorGhostText.foreground` and italic (ghostTextView.css), the text of the line moved after the ghost text in `editor.foreground`, tabs expanded to the tab size; control characters, ligature settings and `stopRenderingLineAfter` are not applied, and the lines are not wrapped (Monaco's are not either). The `ghost-text-hidden` class (Monaco: `opacity: 0; font-size: 0`) is a `hidden` decoration: the text moved to the zone takes no room on the line in both. Tests: `InlineCompletionsEditorTest.testGhostTextAfterTheCursorAndLinesInAViewZone`, `testGhostTextInsideALineHidesTheRestOfTheLine`, the inline scene of tests/visual.
- **Providers answering at once.** A provider that gives its result at once is seen at once (Cityscape's `Promise` settles synchronously, Monaco awaits a microtask): an explicit trigger with no pending request shows the ghost text before `triggerExplicitly` returns. The sequence of ghost texts is Monaco's (vscode's tests record every intermediate state and pass unchanged). Tests: `InlineCompletionsProviderTest`.
- **Not ported.** The hints toolbar (`showToolbar`, accepted and ignored), the font family of the ghost text (`inlineSuggest.fontFamily`, accepted and ignored: decoration styles have no font family), the accessible view and the accessibility signals. `editor.action.inlineSuggest.trigger` has no keybinding, like Monaco's (Alt+\\ is a VS Code workbench keybinding).
## Semantic tokens and rename

- **Semantic tokens styled like VS Code with VS Code themes.** Monaco's standalone themes never enable semantic highlighting (`semanticHighlighting` is always false) and style a semantic token class with the token rules of the theme (`tokenTheme._match('type.modifier')`). Cityscape keeps that for Monaco themes (token rules), and for a VS Code theme (with `tokenColors`, `VSCodeTheme.toStandaloneThemeData`) does what VS Code does: the theme's `semanticHighlighting` enables semantic highlighting under `'configuredByTheme'`, its `semanticTokenColors` style the classes, and the classes no semantic rule styles take the TextMate rules of the scopes vscode's token classification registry probes (`type`: `entity.name.type` then `support.type`, `variable.readonly`: `variable.other.constant`...), so that a VS Code theme without `semanticTokenColors` colors semantic tokens through its TextMate rules. `semanticTokenColors` of a Monaco theme win over its token rules. The color ids of the styles refer to the token color map in use (the TextMate one when the context has TextMate grammars), which is extended with the colors semantic tokens may take; an explicit `setColorMapOverride` is used as it is. `tokenColorMap` gives those colors (Monaco's standalone theme gives `[]`). Tests: `SemanticTokensTest`.
- **Debounce of the semantic tokens requests.** Monaco's `ILanguageFeatureDebounceService` keeps the timings of each model and set of providers in a global service; Cityscape keeps them per model coloring and per editor (the same sliding average of 6 between 300 ms and 2 s for documents, 100 ms and 500 ms for the viewport). The first request is immediate in both. Tests: `DocumentSemanticTokensTest`.
- **Rename messages and notifications.** The reason a provider rejects a location (`MessageController` in Monaco), the reason it rejects the edits, "Rename failed to compute edits" and "Rename failed to apply edits" (notifications in Monaco) go to `Cityscape.onNoResult` with the position of the rename. The progress indicator, the aria announcement and the telemetry are not ported. Tests: `RenameTest`.
- **Rename input.** The input is the kit's `Input` in a box with Monaco's look (renameWidget.css and `_updateStyles`), placed below the line (or above) by Monaco's content widget rules. The new symbol names suggestions (their list, button and providers) and the preview (`acceptRenameInputWithPreview`, the label "{0} to Rename, {1} to Preview") are not ported: the standalone editor has no preview handler, so the command stays unavailable like there. When the editor loses the focus the input is cancelled without focusing the editor again (Monaco focuses it again when the whole window lost the focus). Tests: `RenameTest`.
